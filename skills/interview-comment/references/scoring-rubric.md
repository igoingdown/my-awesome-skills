# 候选人评分细则（打分时读）

配合 SKILL.md「评分体系」的档位定义与严格原则使用。本文件是五维判据、AI coding 专项、传统算法/编程题专项、五维→综合分映射的完整展开。

## 五维度定性判断

五个维度：**业务理解、技术支撑、技术广度、技术深度、软素质**

每个维度用 `+` / `=` / `-` 标注：

| 标注 | 含义 |
|------|------|
| `+` | 加分项：该维度有明显亮点，有证据支撑 |
| `=` | 持平：符合岗位预期，无明显亮点或硬伤 |
| `-` | 减分项：该维度有明显不足或答错 |
| 未考核 | 本轮未覆盖 → **留空、不记录**（不要勉强给 `=`） |

### 各维度含义

#### 1. 业务理解

候选人对所做业务的理解深度。

- 核心判断：能否讲清业务目标 → 技术方案的映射
- 是否用业务指标而非单纯技术指标衡量成败
- 是否关心 ROI、成本、SLA
- **后端**：能否讲清接口/系统服务的上游业务、量级、关键 SLO
- **算法**：能否讲清模型优化指标 vs 业务指标的差异、badcase 驱动迭代经验
- **大数据**：能否讲清数据产品的消费方、SLA、数据 → 决策链路

#### 2. 技术支撑

候选人的技术能力能否真正支撑业务目标。

- 核心判断：技术选型的决策链路是否清楚、trade-off 意识、上线后真实表现
- 是否能讲出"为什么不选另一种方案"
- 是否有量级估算习惯
- `-` 红旗：把"我们用 Redis"当成设计题答案；扩展性追问直接卡死

#### 3. 技术广度

候选人技术栈的覆盖面。

- 核心判断：岗位相邻领域是否接触过、能否把不同组件串起来
- **注意**：广度 ≠ 列一堆名词，能讲清每个东西的**适用场景**才算广度
- `-` 红旗：简历列一堆"熟悉 X/Y/Z"，但任意挑一个都说不出和同类的区别

#### 4. 技术深度

候选人在至少一个领域的深度。

- 核心判断：被追问原理时能答到第几层
- 简历上写"精通 / 熟悉 X"是否经得起追问
- 关键区分：是**背答案**还是**真懂**（追问时是否崩溃/绕开/换话题）
- **AI 时代的归属校验**：候选人陈述的技术点，可能是 AI（编程工具/助手）替他写或说的，而非他本人掌握。对其方案里的**关键技术点抽查原理**（如"你用了 Lua，它在这里解决什么？"→ 应答"保证多命令原子性"）。**答不出 → 该技术点不计入其掌握**；若是他**主动提交的方案**却讲不清核心原理，从重处理（接近"答错"而非"没答出"）。
- 区分"没答出"（知识盲区，可接受）vs"答错了"（原理讲反，严重扣分）
- `-` 红旗：把核心概念讲反；简历明确写"精通 X"被问 X 基础原理答不出

##### ⚠️ "概念型选手"识别（八股 vs 实战）

有些候选人看过很多"八股"、能流畅复述概念，但缺乏对关键技术的准确判断与实战落地。**流畅 ≠ 懂**，这类表现最容易被高估。

**触发条件只看可复核的技术事实，不看背景。** 学校、公司、是否海归、口音、语速、是否书面化表达**都不是**触发信号——它们与技术能力无关，把它们当风险先验会产生系统性误判（表达风格差异被当成能力差异）。判定只依据下面 3 条：

1. **堆概念、无技术细节**：问"X 怎么实现的"，只会复述定义/比喻（如"skill 就像训练新员工把过程告诉他""大概几百行吧"），始终落不到具体实现 → 技术深度 `-`。**需至少 2 个相互独立的技术追问都停在概念层**才触发（单次答不上可能是紧张或该点确实没做过），并在报告里写明这 2 次追问分别是什么。
2. **架构理由站不住**：问某个架构决策（如"为什么不用 multi-cluster / 分库分表 / 某方案"），给的理由经不起一句反问就崩（如"原系统本来就是大 key，跟你的改造有什么关系？"→ 候选人承认"没仔细考虑过"）→ 技术支撑 `-`。**列了多个候选方案 ≠ trade-off 加分**，要看理由是否成立。
3. **关键技术答反**：刁钻题问到核心机制，候选人自信答错（如"多个 Agent 能否共用一个 MCP Server？"——正解：**STDIO 是单进程 stdin/stdout 管道，不能多路复用，必须为每个 Agent 起独立 server 实例**；答"共用相同 credential 不会有问题"是把 I/O 复用问题误判成鉴权问题，**答反**）→ 技术深度红旗 `-`，从重。
   - ⚠️ **判"答反"前必须读完整段拉锯**。真实教训：某候选人被问双通路时效性，首句是"不应该出现这种问题，都是同一个数据源"，据此判了"答错"；但回原文发现**他在同一分钟内就自己补了"那其实他那数据就是有延迟"**，并给出了完整正确的方案（以 Redis 为准 + double check + 版本号）。初版只引了首句和末句、漏引中间的自我修正，把"表述路径曲折"误判成"答错"，被外部评审改判上调一档。**引用要覆盖完整对话段，别只挑首末两句。**

**表达问题单独记，不触发技术负项。** "自我介绍漂移、抓不住重点、非结论先行、卡顿"这类只进软素质与「面试官复盘·表达效率」的观察，**不得据此判技术深度/技术支撑 `-`**。别把"信息量大 / 书面化流畅"误读成"结构化"——结构化是结论先行、点出价值与难点，不是话多；但反过来，表达不结构化也不代表技术不行。

**判分铁律**：核心维度（技术深度 / 技术支撑）**在已充分取样的前提下**被追问穿或答反 → 即便其他维度有 `+`，综合 **≤ 2.5 不通过**；前面的 `+` 被实质抵消。诚实承认边界是软素质中性项，**不能**用来把技术硬缺口洗成加分。**判 `+` 前先自问：这个亮点扛住面试官的犀利追问了吗？**

> ⚠️ 铁律的触发前提是"取样充分"。若该维度根本没问到（或只问了 1-2 个边缘问题就换题），走 SKILL.md「证据充分性前置门」留空，**不得**用本铁律压分。另外要区分"大厂分工"与"能力缺陷"：候选人说"这块是数仓/中间件团队做的、我提工单"，在分工细化的大厂属正常协作边界，**不构成技术支撑 `-`**（`-` 的红旗是"把'我们用 Redis'当设计答案""扩展性追问直接卡死"）；它影响的是"负责人含金量"的判断，应记在贡献边界一节，不是技术扣分项。

**岗位细化关注点**：

- **后端**：并发与锁、MySQL 索引/事务/MVCC、缓存一致性、MQ 语义、分布式 CAP
- **算法**：模型原理（loss/优化器/反向传播）、训练/推理工程瓶颈、实验设计与指标体系
- **大数据**：Spark/Flink 执行原理、shuffle、数据倾斜、state/exactly-once、数据建模分层

#### 5. 软素质

沟通、学习、价值观、稳定性的综合判断。

- 回答是否结构化（先结论再展开）
- 对追问的反应（积极重组 vs 不耐烦/抵触）
- 跳槽节奏是否合理、对前司是否明显情绪化
- 对"近期学了什么"能否答出有说服力内容
- **工作抽象与自我表达**：能否主动、有重点地讲出自己工作的价值与难点（结论先行 / STAR）。**判定规则：若候选人靠面试官逐层追问才讲出真实工作内容与难点（自己开口讲不出重点、抽象不出价值），此情形不作为软素质减分，但明确不能作为加分项（软素质最高只能 `=`）。** 可交叉看简历是否同样"堆功能、不点价值"。
- **红线**：价值观问题（如对同事的不当评价、歧视言论、"卷同事"当荣誉）→ 直接 `-`，且综合分不得高于 2.5

## AI coding 题专项评估

当本轮编码/设计题是 **AI coding 题**（允许候选人使用任意 AI 编程工具、投屏，面试官扮演产品经理只答非技术问题）时，**评估的是"用 AI 的过程与落地细致度"，不是代码能否跑通**（代码 AI 随时能写）。

### ⚠️ 不能只凭 asr 转写文本判 AI coding 题

转写记录的是"候选人最终说出的话"，其中很可能包含**AI 产出的完整、书面化文本**——这会让候选人显得很强、流程很完整，但**那是 AI 的完整，不是候选人能力的完整**。真实水平藏在屏幕操作过程里（怎么写第一个 prompt、有没有选型、有没有测试、被问才补还是主动做）。**评估必须结合面试官现场观察 / 屏幕过程；遇到转写在编码环节突然变得高度书面化、结构化，更要警惕这是 AI 产出而非本人现场表达，不可因"转写流畅"就给高分。**

### 过程清单（必需项，逐条核对）

任一项缺失，在对应维度如实体现（多为 AI 应用能力、技术广度的待提升，必要时落到技术支撑/技术深度）：

1. **需求澄清**：是否主动挖隐含条件/边界（如是否多机、限流维度、量级、并发要求），还是直接把需求原样扔给 AI 取第一版。
2. **方案选型**：是否对比多方案再决策（如限流的令牌桶 / 漏桶 / 滑动窗口），还是照单全收 AI 给的单一方案、无 trade-off。
3. **过程拆解**：是否先让 AI 出设计 / 拆 Task / 定验证（Verification）Plan，再分块实现，而非一句"帮我写个 X"。
4. **质量保障**：写完是否做**功能测试 + 性能测试**，到可交付状态。
5. **代码 review**：过程中是否对 AI 产出做交叉 code review。
6. **原理归属校验**：对 AI 生成的关键技术点抽查原理（见「技术深度 · AI 时代的归属校验」）。讲不清 → 该技术点不计入其能力；主动提交的方案讲不清核心原理，从重。

### 判分锚点

- **加分（AI 应用是真能力）**：主动澄清隐含条件 + 做方案选型对比 + 先方案后代码 + 主动写功能/性能测试 + 对产出能讲清原理并 review。能"现场驱动 AI 高效逼近一个可交付方案"。
- **地板（不加分）**：把需求交给 AI 让它写出来、能复述"标准 AI 协作流程"，但选型/测试/校验都靠面试官追问才补。
- **减分**：直接扔题不选型、不做测试、被问才改关键设计（如多机）、AI 生成的关键技术点讲不清原理（归属校验失败）。

> 提示：本节与团队既有的"识破不懂装懂要切替代评估"一脉相承——对 AI 产出的关键点追问原理，本质就是一次"归属校验 / 替代评估"，能当场把"AI 替他说的"和"他真懂的"区分开。

## 传统算法/编程题专项评估

当本轮是**传统算法/编程题**（面试官出题、候选人手写代码或口述解法，不允许用 AI）时，用这一节。**评估的是"能否独立收敛到一个正确、可运行的解法"**，与 AI coding 题的"用 AI 的过程"是两套标准，不要混用。

### 先定性：这道题落到了哪一档形态

先明确本轮编码到了哪一步——形态直接决定能给的最高分：

| 形态 | 说明 | 判分基调 |
|------|------|---------|
| 写了代码 + 自己跑通/走查 | 有 `candidate-code.<ext>`，运行记录非空或有口头走查 | 可正常给分，按正确性判 |
| 写了代码 + 零自测 | 有代码，但平台可运行而运行记录为空、也没走查 | 无论对错都要记"自我验证习惯缺失"这一负向项 |
| 只口述、没落代码 | **给了足够时间**却全程"口述跑一遍"，无代码产出 | 编码落地能力**未验证**，对中高级岗天然封顶（口述再顺也不等于能写对） |
| 靠面试官点破才通 | 候选人卡住，正确解法是面试官说出来的 | 独立解题能力**未达标**，是压分项，不能算"做出来了" |
| **未取样（时间不足）** | 编码只剩几分钟 / 面试官明说"来不及写了" / 环节被砍 | **走「证据充分性前置门」：技术深度留空，不记 `-`、不压分。**缺口记面试官账上（节奏控制 `✗`），并写进下一轮补测清单。已观察到的信号（如读错题）可如实记录但注明不作判分依据 |

### ⚠️ 必做：把候选人代码真的跑一遍

**只要拿到了 `candidate-code.<ext>`，就必须用题目自带的示例用例实测，不能靠肉眼判断对错。** 这是本 skill 最容易翻车、也最能拉开判断精度的一步——真实案例里，一段"结构清晰、命名规范、看起来对"的代码，跑一遍才发现在题目给的第一个用例上就输出错误答案。

- 用 node/python/go 等把代码补成可运行片段（去掉 TS 类型、包一层 main），喂题面的每个示例用例，比对期望输出。
- 若怀疑算法层面有反例（如贪心/双指针），**主动构造反例并跑验证**，不要停在"双方都想不出反例所以放行"——想不出反例 ≠ 没有反例。
- 把"实测 X 用例期望 True 实际 False"这类结论写进 `coding-analysis.md`，作为判分的硬证据。

### 审查清单（有代码时逐条核对，写入 coding-analysis.md）

1. **题意转化 / 需求澄清**：是否主动澄清歧义（如"子数组要不要连续""能不能重叠"）、用示例自验证理解、给出可行性剪枝。
2. **问题分解**：主循环/辅助函数拆分是否合理，子问题抽象是否正确。
3. **算法正确性**：算法选型能否覆盖题目全部情况。⚠️ 特别核对**实现的算法与口述的思路是否一致**——真实案例里候选人口述"找任意子集"、代码却写成"找连续窗口"，是两道不同的题。
4. **实现正确性**：边界、off-by-one、越界、类型；以实测结果为准。
5. **完成度**：题目所有要求是否都实现（如"有解要输出一组解"这类附加要求常被漏掉）；脚手架/模板代码（如 `console.log("Hello World!")`）是否清理。
6. **自我验证习惯**：写完有没有跑用例/走查。平台可运行却运行记录为空 → 明确记负向。
7. **复杂度意识**：是否主动分析时间/空间复杂度、自评 TLE 风险。
8. **作答独立性**：结合页面切换记录，中途有无长时间离开（疑似查资料/问 AI）。

### 判分锚点（按资历校准，见「评分体系 · 资历×深度期望」）

> ⚠️ **先过 SKILL.md 的「证据充分性前置门」**：编码环节时间不足（如只剩几分钟、面试官明说"来不及写了"、环节被砍）属于**未取样**，技术深度**留空**，不走下面任何一档。下面的档位只适用于"给了足够时间"的情形。

- **加分**：独立收敛到正确解法 + 边界处理干净 + 主动跑用例自验证 + 复杂度分析到位。
- **中性/持平**：思路正确方向、能自我发现 badcase、但实现有非致命瑕疵；或题目偏难、在合理提示下自己爬出来。
- **压分（够不到中高级期望）**：只口述没落代码、中等题独立写不出、靠面试官点破才通。这类情形对中高级岗**是压分项而非直接判死**——若展现了一定算法推理（如能自己举反例、可行性剪枝对），技术深度封顶 `=` 而非直接 `-`。**这一条与 SKILL.md「资历校准·达不到资历期望即降档」曾出现字面冲突（同一事实一边判 `-` 压 ≤2.5、一边封顶 `=`），已统一：以本节形态表 + 前置门为准。**
- **判死（技术深度 `-`，综合 ≤2.5）**：交付了"看起来对、实测错"的代码且零自测；或把核心算法概念讲反。**"写完没验证、实测是错的"比"没写完"更严重**——前者是工程习惯问题，暴露的是"自认为对就交付"。

### 区分"没做出来" vs "做错了" vs "没验证"

- **没做出来**（时间不够、卡在某步）：知识/熟练度问题，按资历判，可接受度较高。
- **做错了**（算法用错、概念讲反）：严重，尤其主动提交的解法。
- **没验证**（有平台不跑、写完不走查）：工程素养问题，无论对错都要如实记；若"没验证"叠加"实测是错的"，从重。

> 提示：中高级岗对"中等题落地一个正确解法"的期望是硬线。口述得再流畅、思路方向再对，**没落到正确可运行代码，就不能当作"这题做出来了"**——这与"广度/流畅不能冒充深度"是同一条反陷阱原则。

## 五维打标 → 综合分 映射（参考）

| 五维情况 | 参考综合分 |
|---------|-----------|
| 3+ 个 `+`，其余 `=`，无 `-` | 3.5 ~ 4 |
| 1~2 个 `+`，其余 `=`，无 `-` | 3+ ~ 3.5 |
| 全 `=`，无 `-`，无 `+` | 3（此时走严格原则，**大概率打 3 不通过**） |
| 有 1 个 `-`（非技术深度/技术支撑） | 3 或更低 |
| 技术深度 `-` 或 技术支撑 `-` | 2.5 或更低 |
| 软素质价值观红线 `-` | ≤ 2.5 |
| 多个 `-` | 2 |

**含"未考核（留空）"维度时怎么算**（原表只列了 `+`/`=`/`-` 的组合，留空维度如何参与打分曾无定义，导致同一份材料既可能被当成"无负面证据"也可能被保守当成 `-`）：

| 情况 | 处理 |
|---|---|
| 岗位**核心维度**留空（后端/算法/大数据：技术深度、技术支撑任一） | **分数只用已取样维度算**，留空维度既不加分也不减分；概览必须写"X 维度本轮未取样，证据面不完整，建议下一轮补测后终判"；**不得**给 ≥3+（证据不足撑不起通过线），也**不得**因留空而压到 ≤2.5。⚠️ **本条只封分数上限，不封面试官的 3 档裁定权**——落 3 后面试官仍可基于现场体验裁定通过，见下方「⚠️ 分数上限 ≠ 结论上限」 |
| **非核心维度**留空（业务理解/技术广度/软素质之一） | 分数只用已取样维度算，概览注明覆盖率即可，可正常给到 3+ 及以上 |
| 留空 ≥3 个维度 | 材料不足以支撑评价，**不出分**，报告写"取样不足，无法给出综合评分"+ 补测清单 |

注：这是参考映射，不是硬性公式。最终分数必须结合证据强度判断，但**不得违反"严格原则"硬规则与「证据充分性前置门」**。

### ⚠️ 分数上限 ≠ 结论上限（AI 不得用"证据不足"否决面试官的 3 档裁定）

**真实事故**：某校招场（对标 1-2）后端基础零考察、编码零产出，AI 据「核心维度留空不得给 ≥3+」把分数从 3+ 下调为 3——**这一步是对的**。但接着 AI 写了"这里**不做裁定**，因为缺的不是'某个短板可后天补'，而是校招最核心的两项根本没测，应当补测而非裁定"，把结论定成"不通过/待补测"。面试官随后指出：候选人业务有 sense（点破后能自己想清楚）、记忆方向工作扎实、算法题反应快、做事方法有量化验证闭环，**愿意给 3 分通过**。AI 的"不做裁定"是自己加的限制，规则里没有。

**两条硬边界：**

1. **"不得给 ≥3+" 约束的是分数，不是结论。** 3 档裁定权是 `SKILL.md`「通过标准」明文给面试官的独立权力。AI 把分数落到 3 之后，**必须保留裁定路径**，在概览写"打 3，等待/已获面试官裁定"，**不得**自行写成"不做裁定""应当补测而非裁定""证据不足不予通过"。取样不足是**下一轮补测的理由**，不是**本轮否决裁定的理由**。
2. **AI 的观测盲区不能用来否决面试官的现场观测。** AI 只有 ASR 转写 + 简历；反应速度、吸收提示的速度、冲劲、现场紧张程度、是否边想边说——**这些转写里根本不存在**（见 SKILL.md「面试官现场观察可参与裁定」）。用"我没看到足够证据"去否决"面试官现场看到了"，是把自己的信息缺失当成候选人的缺陷。

**判定动作**：写结论前自查一句——**"我是在报告分数，还是在替面试官做裁定？"** 分数由证据定，裁定由面试官定。二者冲突时（如 AI 判 3 默认倾向不通过、面试官裁定通过），**以面试官为准**，并在概览留痕两者的理由。

> 附带一条容易连带犯的错：**"被点破后能自己想清楚"不等于"结论是面试官给的"。** 同一事故里，AI 把候选人 14:18「确实是的」之后**自己举例把价值讲清楚**的整段（举了 iPhone 17/18 对比、联系自身使用体验、自己收口到"初衷是让用户更高效检索"）写成了"候选人只是附和，结论是面试官推出来的"。正确读法：承认之后**是否还有自主输出**——有，就是"吸收提示快"（校招正向信号，不计加分但绝不记负向）；没有、只答"对"，才是"靠面试官喂"。**判这一条必须读完承认之后的整段，不要停在"确实是的"这句。**

> **关于 3 档的裁定**：当五维指向 3+（如 1 个 `+` 其余 `=`）但存在隐性短板（如 AI 应用能力弱、方案选型缺失、关键数据掌控差）把综合压在 3 时，可落 **3**，并由面试官裁定是否通过——若裁定通过，在概览写明"打 3，面试官裁定通过"及理由（如核心维度有真实底子、短板可入职后习得）。**`+` 维度没有自动把综合顶到 3+ 时，要在概览说明是哪些隐性短板拉低了它。**

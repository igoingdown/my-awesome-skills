# 二次评估 + 反模式 + 案例

## 步骤 4+5：本 Agent 二次评估 CodeX 的报告（最关键，别省）

CodeX 完成后**不要直接把它的结论丢给用户**。CodeX 也会夸大、误读、定级偏重，甚至**给出失效或牵强的 SOP 出处**。本 Agent 必须**逐条回到代码里复核**，并**核验它引用的每个 SOP URL 是否真实、权威、确实支撑该结论**。

对每条 finding 判定：

- **✅ 属实** —— 复核代码确认成立 → 该改。
- **⚠️ 属实但定级过重** —— 问题真实但危害/概率被高估（如把"窄窗口、低危害、可自愈"的问题定成 BLOCKER）→ 降级，说明理由。
- **❌ 误读/夸大** —— CodeX 误解了原意，或代码并非它说的那样 → 反驳，引代码证据。
- **🔗 SOP 出处核验** —— URL 是否可达？是否权威源（官方文档/OWASP/RFC 等）而非随手博客？该源是否真支持这条建议？出处站不住的，把建议降级为"观点"。
- **🔮 推测风险 vs 线上实锤** —— finding 声称的危害（如"每天上万次泄露占位句""缓存竞态导致用户看到脏数据"）是**代码路径推演出的担心**，还是**线上真发生过且有日志/trace/数据实锤**？两者处置完全不同：语义明确、模型/系统大概率不会踩的推测风险，即便代码上"可能发生"，没有线上证据就不该按已实锤问题定高级别。复核时要求区分并在净结论里标注「推测 / 已实锤」——能拉一条命中 trace 或一行计数就是实锤，拉不到就明说"未在线上观察到，属预防性"。这是用户反复追问的点（"这是你推测的还是线上确实发生了？有实锤吗？"）。
- 区分 **must-fix** 与 **过度设计建议**（CodeX 常爱加新字段/新抽象，对低频功能往往不值当）。

最后给用户一个**净结论**：综合 CodeX + 本 Agent 复核后，能不能开工/合入、之前需要改哪几处。

## 步骤 6：往 PR 上发评论前必须先跟用户对齐

净结论留在本地是内部产物，**发到 PR / MR 上就是对外发言**，署的是用户的名。评审对象是他人 PR 时尤其如此：定级偏重或事实说错，返工成本落在协作方身上。

顺序固定为「先核实 → 再解释 → 对齐后才发」：

1. 复核完先把每条 finding 跟用户讲一遍：问题是什么、凭什么成立（引真实 `file:line`）、建议定级。
2. 等用户逐条裁定。用户常做两类调整：**改措辞**（同一问题换更准确/更克制的说法）和**降级**（P1 → P2，认为危害被高估）。裁定以用户为准，不要在评论里悄悄保留自己的原定级。
3. 用户确认后才调用发评论的通路。未确认前，findings 只落本地文件。

反模式：复核完直接把 findings 批量发成 PR 评论——用户明确要求过「我们对齐之后，再发布 review 评论」。

## 反模式（别这么干）

- ❌ 用本 Agent 自己的 Sub-Agent（Task/Agent 工具）冒充 CodeX —— 违背"独立第二意见"的全部意义。
- ❌ 不加 `--search` —— "SOP 必带来源"会落空，CodeX 只能凭记忆空谈。
- ❌ 推理强度用默认/low —— 对抗式深评必须 `xhigh`。
- ❌ 同步阻塞等 CodeX / 用 `sleep` 轮询 —— 用后台 + 完成通知。
- ❌ 把 CodeX 的报告原样转述给用户 —— 必须先逐条复核 + 核验 SOP 出处，CodeX 不是权威。
- ❌ 接受无出处的"最佳实践"建议 —— 没有权威 URL 的 SOP 一律降级为观点。
- ❌ 让 CodeX 顺手改代码 —— 评审与实现严格分离，指令里明令只写评审文件。
- ❌ 全盘照单全收 CodeX 建议 —— 尤其它爱加的新字段/新抽象，对低频功能多半是过度设计。
- ❌ 未经用户对齐就把 findings 发成 PR 评论 —— 对外发言必须先核实、再解释、对齐后才发（见步骤 6）。
- ❌ 只送 spec 或只送 implementation —— 分层文档要一起送并加层间一致性检查，否则漏「详细设计跑偏」或漏「根因不成立」。
- ❌ 先评「方案好不好」再想「还要不要做」 —— 线上既有机制可能已解决该问题，必要性问题优先于正确性问题。
- ❌ 认可一个「现状看起来不合理所以要改」的方案而不追问现状的设计来源 —— 先查 blame / 原始 PR 确认现状是不是有意为之，否则可能在修不存在的问题。
- ❌ 放过注释/文档里没有依据的因果断言 —— 「这样写会导致 X」是结论，要么给出线上或实验依据，要么标注为假设。

## 一个完整案例（本 skill 的来源）

`specs/2026-06-24-admin-review-globe-key-no-gating/`（文档+代码交叉评审）：

- `codex-review-prompt.md` —— 对抗式评审指令（要求逐条核码、固定输出结构）。
- `codex-review.md` —— CodeX 产出（Verdict: No；1 BLOCKER + 3 MAJOR + 2 MINOR + 1 NIT）。
- 本 Agent 二次评估：复核后认为 BLOCKER 属实但**定级过重**（窄窗口、低危害、可自愈），其余 6 条 5 条属实、1 条误读 spec；净结论"可开工，开工前做 4 处小修"，并据此修订了 spec。

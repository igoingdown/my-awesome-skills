# 评审指令必含要素 + 输出结构

写评审指令时，先定**评审对象**（决定 prompt 保留哪些段落）：
- **A. 只评审文档**（spec / 设计方案）
- **B. 只评审代码**（一段实现 / 一个 PR / 一组文件 / 一个 diff）
- **C. 文档 + 代码（推荐）**——重点是交叉验证

**文档是分层的两份时（spec 概要设计 + implementation 详细设计）一起送审，别只送一份**：两份都进材料清单，并额外要求一项**层间一致性检查**——spec 里的每条约束/风险在 implementation 里有没有对应的落地动作；implementation 有没有引入 spec 没批准的范围（多改的文件、多加的字段、顺手做的重构）。只送 spec 会漏掉「详细设计跑偏」，只送 implementation 会漏掉「方案层根因不成立」。

> 填空式模板见 `../review-prompt-template.md`，已内置 A/B/C 三种对象的取舍说明。

## 指令必须包含的要素

1. **角色定位**：明确要求"DEEP, ADVERSARIAL（深度对抗式）"，**be adversarial, not agreeable**（找茬，别附和）。
2. **上下文**：项目名 + 一句话技术栈 + 评审对象 + 它想解决什么。
3. **待评审材料**：文档路径 / 代码范围 / 关键文件清单（引导 CodeX 去核）。
4. **评审方法硬要求**：
   - **回到真实代码核对**：不信任何 file:line 引用、注释、commit message、散文描述——自己打开文件看，磁盘上的代码才是真相。
   - **先对齐最新远端再交叉验证**：交叉验证前先确认代码是当前 main/dev 的最新状态（评审启动前拉一次远端）；文档 / spec 里对代码的断言可能基于早已合入或推翻的旧实现，交叉验证要以最新代码为准，并把「文档描述的是已过期的实现」单列为 finding，别拿旧代码去印证旧文档得出「一致」的假结论。
   - **文档↔代码交叉验证**（对象含两者时）：文档每条关于代码的断言逐条回代码核是否属实；方案是否匹配代码实际能力（签名、数据形状、可空性、调用顺序、事务边界）；有没有代码现实被文档漏掉、或文档要求无对应代码。
   - **代码↔配置上线错配**：改动依赖外部配置（环境变量 / configmap / 开关 / 定时任务）时，检查「代码先上、配置没跟上」这个时间窗的行为——此时链路是否安全退化到旧路径（fail-safe），还是会走进未配置的死路。要求给出：配置缺失时的兜底行为、主依赖失败能否回退到旧实现、以及一份可逆的回滚 / 回退操作手册。缺兜底或缺回滚手册按 MAJOR 起报。
   - **降级/兜底路径要审"产物质量"，不只审"有没有兜底"**：兜底不能悄悄产出一份看起来正常、实际已失真的产物再落库或下发——本地截断、占位内容、简化算法顶替主链路结果，都是把失真固化成正式数据，之后没人知道这条是降级来的，后续所有基于它的度量和体验都带着这个偏差。逐条核降级产物的去向：凡写库 / 进缓存 / 拼进下游输入的，按 MAJOR 起报，要求改成「先重试 → 仍失败则丢弃，同时把重建所需的输入完整打进日志，事后可捞回重放」，并给出失真产物的可识别标记与回补路径。用户的原话形态是「退回本地截断是不应该的，应该重试，重试失败就直接丢弃、把生产所需数据打出来、通过日志捞回重放即可，截断改写产物绝对不可取，这个设计有大问题」。
   - **结论建立在模型判断上时，审判据而不只审结论**：送审材料里若有靠 LLM 打标/打分/语义比对得出的结论（如「实验组输出信息密度更高」「体验受损」），要求逐条核这四项，缺项按 MAJOR 报：(a) **样本量与抽样口径**——抽了多少条、怎么抽的、是否可能偏样，「全量 vs 抽样」必须写明；(b) **代理指标能否支撑结论**——用 token 数、字数、轮数这类易得量代替「信息密度」「满意度」这类目标量时，必须说明代理与目标的关系并做反例检查，不能把「输出 token 变多」直接讲成「内容更密」；(c) **异族模型交叉验证**——同一批数据换不同厂商/不同架构的模型重打一次，两者一致的部分才算结论，不一致的列为待定，单模型打标的强结论按 MAJOR 报；(d) **人工金标校准**——抽一小批人工标注比对模型标签，给出一致率作为模型标签的可信区间。用户为此反复返工（「不能只看 token 个数就说内容更密」「担心结论站不住脚、再次反转」「采用了多少样本，说清楚再写文档」）。
   - **挑战实质**：根因是否成立、方案是否有更优解、边界 case、跨层一致性、成本/延迟是否被低估、fail-safe 是否合理、测试是否覆盖风险点。
   - **新增旁路通道要审"为什么不用平台既有通路"**：方案里出现与平台既有能力平行的第二套通道时（自建轮询做配置热更、自起后台 ticker、在进程入口挂常驻 watcher、绕开既有部署流程的运行时覆盖层），第一问不是"实现得对不对"，而是"既有通路为什么不够"。要求作者写明：平台标准通路（配置注入 + 重启/滚动发布、既有开关系统、既有定时器框架）在这个场景具体差在哪、差多少（是差分钟级时效，还是只是嫌重启麻烦），以及新通道带来的长期成本——两套配置源的取值优先级与不一致排查、进程入口被改动的连带影响、依赖多了一个存储后它挂掉时的行为、以及谁来维护这条只服务一个功能的通路。用户的质疑形态是「不应该自己造旁路，应该依赖平台的配置注入 + 重启来更新配置，这块方案我认为需要改掉，你觉得不能改的原因是啥」。给不出「既有通路确实做不到」的具体依据、或改动侵入了进程入口/全局初始化而没论证必要性的，按 MAJOR 报；即使新通道最终保留，也要求给出与既有通路的边界约定和退场条件。
   - **修复是否建立在对现有设计的错误假设上**：改动声称"现状是错的/不合理"时，要求先给出现状的**设计来源**——这段结构是谁、为什么写成这样（查 blame / 关联 PR / 原始注释），有没有当时的约束在支撑它。只凭"看起来不合理"就动手，很可能是在修一个不存在的问题，甚至破坏现状在保护的东西。用户的追问形态是「这个方案是怎么来的、是谁写的、这样设计的好处是什么？你是不是基于一个错误的假设在做修复？如果是，这修复就没必要」。缺这段溯源、或溯源后发现现状是有意为之而改动没回应那个意图的，按 MAJOR 报。
   - **注释与文档里的因果断言同样要有依据**：代码注释/spec 里写"之所以这样做是因为 X 会导致 Y"（如某种写法会诱导模型产生某种行为）属于结论，不是说明。要求逐条标注依据来源（线上 case / 实验对比 / 权威出处），拿不出的改写为假设并明确标注。用户会直接查证并追问「这行注释所在的改动，你实锤过吗？我看了 case 并没发现这类问题，你能证明吗」——把无依据的因果叙事写进注释，等于把推测固化成团队共识。
   - **问题是否已被线上既有能力解决（先问必要性再问正确性）**：评审方案/spec 时，第一问不是「这个方案对不对」，而是「这个问题现在还存在吗」。已上线的机制可能已经覆盖了该 spec 想解决的场景，此时正确结论是「不必做」而非「做得更好」。要求逐条比对：spec 声称要解决的每个问题，回最新代码找有没有现成机制已经处理；若已处理，把该 spec / 该子任务标为**可裁撤**并说明依据。反向也要查：若既有机制只覆盖了一部分，明确划出仍需补的边界，避免为了「覆盖不全」而重造整套。这是用户反复追问的点（「线上已有 X 机制了，当前方案有没有过度设计嫌疑，要解决的问题到底是什么」）。
   - **失败姿态（fail-open / fail-close）必须逐分支写明，且不许悄悄改变**：改动引入校验、白名单、映射查表、开关判断时，问清"这一步查不到 / 报错 / 超时时，请求是继续放过还是直接拒绝"，以及**改动前是哪一种**。最常见的隐蔽退化是原本兜底放过的路径被改成命中不到就拒，用户侧表现为功能整块不可用而日志只有一行校验失败。要求作者给出三件事：触发 fail-close 的**具体条件枚举**、每种条件下的**用户可见表现**、以及改动前后姿态是否变了；姿态发生变化而 spec 没写的按 MAJOR 报。选 fail-close 时要有理由（宁缺勿错的合规/资金场景），选 fail-open 时要有观测（放过了多少、放过的是什么），两者都缺即为 finding。审"换供应商 / 换模型 / 换渠道"这类替换时同理：**逐环境枚举配置形态**（各环境的凭据位置、项目标识、地址、参数名可能完全不同），只在一个环境验证通过就宣称兼容的按 MAJOR 报，并要求给出"某环境缺这项配置时是降级还是启动失败"。
   - **SOP 取证（关键）**：用 **Web Search 工具**给最佳实践类建议取证；**每条 SOP/反模式/业界标准必须带权威出处（名称 + 可解析 URL，必要时含章节/版本）**，并与在审代码/文档**交叉验证后**给出；找不到权威源就如实说明并降级为"个人观点"，不得把无源建议包装成标准。
   - **可观测性审查（上线硬门槛）**：核心链路缺观测依据按 MAJOR 起报，不是 NIT。
     - **日志**：异常分支必须有明确错误日志，禁止静默吞错；日志要简短，且带能与其他业务隔离的检索关键词——关键词必须是**不含空格的单词、CamelCase**（如 `GiftBatchDeductFail`），因为分词型日志系统（如 SLS）按空格/标点切词，多词短语无法精确检索；`error`/`failed` 这类通用词、或与无关链路共用的词都算 finding。
     - **打点**：核心业务链路（正常+异常）必须构成可观测漏斗——入口、关键分支、成功、各失败原因分别可数，能回答"请求在哪一层掉了"；打点方式以项目现有惯用法为准，不强推特定库。若改动以性能优化为目的，必须有覆盖优化路径的耗时打点，否则效果上线后不可验证，按 BLOCKER 报。
     - **观测本身的开销与执行时机**：观测代码不能反过来拖累线上。逐条核：(1) **日志量级**——高频链路（每请求都走的路径、循环体内）加的日志会不会刷爆日志系统、单条日志体积是否可控，热路径上打大对象/整段 payload/长字符串按 finding 报，要求采样或只打关键字段；(2) **同步 vs 异步**——观测埋点/日志/上报是否卡在业务主链路同步执行，同步写外部（远程日志、指标上报、DB）会给每个请求叠加延迟，热路径上应走异步/本地缓冲/批量，明确要求作者说清 helper 是同步还是异步及其对 P99 的影响；(3) 缺这两项分析、或热路径上确有同步重日志的，按 MAJOR 起报。用户反复追问「日志长度多少、会不会因为打太多日志影响线上性能、helper 是同步还是异步」，观测方案必须自带这份开销评估。
     - **文档评审**同理：spec 必须写明观测方案（失败路径日志关键词、核心链路漏斗、耗时敏感点的耗时打点），只定义行为不定义如何观测的 spec 视为不完整；观测方案还要写清热路径日志的量级与同步/异步执行时机，不能只加观测不评估其开销。
   - **PR 内容边界（合入纪律）**：评审对象是 PR/diff 时，检查是否混入了不该随代码合入的非代码产物——spec/设计文档、监控看板/告警 JSON 等部署产物出现在业务代码 PR 里，按 MAJOR 报并要求移出（spec 留在项目文档目录或协作平台，监控产物走各自的推送通道、本地留档）。纪律是「代码 PR 只进代码」，用户已多次因此返工剥离。
5. **约束**：**只写评审文件，不许改任何源代码。**

## 强制输出结构

要求 CodeX 把评审写到指定路径 `codex-review.md`，结构固定：

- **Verdict**（yes / yes-with-changes / no）
- **Findings**：每条标严重度（BLOCKER / MAJOR / MINOR / NIT）+ claim/代码位置 + 代码验证（引真实 `file:line`；交叉评审时给"文档断言 vs 代码现实"）+ 为什么是问题 + 具体修法 + **若涉及 SOP 则附出处名 + URL**
- **Sources cited**：所有用到的 SOP/标准/参考 URL 汇总清单（便于逐条核验）
- **What the target got right**（避免回归已验证的正确决策）
- **Open questions**（开工/合入前必须回答的问题）

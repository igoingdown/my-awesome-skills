# 输出文件模板（写报告时读）

每次评估固定产出**两个文件**，均写入 `<人名>/<目标轮目录>/`；本轮有编程题时另加编码产物：

| 文件 | 内容 | 用途 |
|------|------|------|
| `evaluation.md` | 候选人评价（五维打标 + 评分 + 面试记录） | **对外交付物——会被整段复制粘贴进公司招聘系统留档** |
| `interviewer-review.md` | 面试官复盘（五维评估 + 做得好/不好 + 改进建议） | 面试官自用，持续改进 |
| `coding-analysis.md`（有编程题时） | 题面 + 审查清单 + 实测结果 + 反例 | 编码环节判分的硬证据（内部） |
| `candidate-code.<ext>`（有代码时） | 候选人代码原文 | 供实跑与逐行审查（内部） |
| `review-log.md`（**有改判时新增**） | 评审与改判的全部过程留痕 | 内部追溯用，**绝不进 evaluation.md** |

## ⚠️ evaluation.md 是对外交付物：零过程性内容（硬规则）

**用户会把 `evaluation.md` 的内容直接贴到公司招聘网站作为正式记录。** 读者是 HR、后续轮面试官、评审委员会——他们要的是"这个候选人怎么样"，不是"这份评价是怎么写出来的"。

**以下内容一律不得出现在 `evaluation.md` 里**（真实事故：三份报告里各有 6-21 行这类内容，用户明确要求全部删掉）：

| 禁止 | 典型措辞 |
|---|---|
| 版本与改判痕迹 | `v1`/`v2`、"初判 X 改为 Y"、"改判说明"、"三次演进"、"~~删除线~~" |
| 评审过程 | "经 CodeX 评审"、"GPT-6 指出"、"外部评审复核后"、"子代理复核" |
| 自我纠错叙事 | "我上一轮的失误"、"我误读了"、"初版写成了…"、"这条我改过头了" |
| 规则援引与元讨论 | "按 skill 前置门"、"按映射表规则"、"违反了硬规则第 N 条"、"不触发铁律" |
| 撤销/保留的记账 | "撤销第三处"、"这条保留"、"下调为"、"从三处改为两处" |

**正确做法：写成"当前唯一结论"的样子。** 结论就是结论，证据就是证据，不解释它经历过什么。

- ❌ `技术深度：v1 判 `-`，v2 撤销后改 `=`（LRU 那条经复核不成立）`
- ✅ `技术深度：=`（正文只陈述当前判断依据，不提曾经判过什么）
- ❌ `**v2 修正**：简历技能栏根本没有 ES，v1 写"把 ES 列进技能表"是事实错误`
- ✅ `ES 倒排索引答得粗（14:38…），但简历技能栏未声称掌握 ES（只写"了解 GO、MySQL、Redis"），且 ES 是他否掉的候选方案，严重度有限`

**改判过程要留痕怎么办？** 写进独立的 `review-log.md`，记：改了哪一条、依据的原话、谁提出的、结论怎么变。`evaluation.md` 只呈现终态。

**判分口径的必要说明可以留，但要写成客观事实而非规则援引：**
- ❌ "按 skill 证据充分性前置门，编码未取样不作负向证据"
- ✅ "编码环节因时间不足未能验证（面试官出题时即说明「应该没时间写了」），本轮不作为候选人的能力判断依据"

## 候选人评价模板（evaluation.md）

**严格按**下面的结构输出。所有斜体占位符替换为真实内容。不要增加、删除、合并、重命名任何一级/二级/三级标题。五维顺序必须是：业务理解 → 技术支撑 → 技术广度 → 技术深度 → 软素质。

````markdown
# 面试评价报告

## 信息汇总

本轮 *N* 面。

**定性判断：**

维度：业务理解、技术支撑、技术广度、技术深度、软素质。
指标：+ 代表加分项、= 代表持平、- 代表减分项，未考核不记录。

| 维度 | 标注 |
|------|------|
| 业务理解 | *+ / = / - 或留空* |
| 技术支撑 | *+ / = / - 或留空* |
| 技术广度 | *+ / = / - 或留空* |
| 技术深度 | *+ / = / - 或留空* |
| 软素质 | *+ / = / - 或留空* |

### 概览

本轮面试按 *目标岗位（校招须写明对标职级，如"校招，对标 1-2"）* 要求，候选人 **X**（*3+ / 非 3+*），**通过 / 不通过 / 打 3，等待面试官裁定**。

*一句话核心理由（≤30 字）。如命中 borderline 严格原则，在此说明："在 X 和 Y 之间犹豫，按严格原则打 X"。若打 3 且裁定通过，写明："打 3，面试官裁定通过——<理由>"。*

*⚠️ 打 3 且面试官尚未表态时，结论写"打 3，等待面试官裁定"并列出裁定所需的关键信息；**不得**写"不做裁定""证据不足不予通过"——裁定权属面试官（见 SKILL.md「通过标准」与 scoring-rubric「分数上限 ≠ 结论上限」）。面试官裁定后在此追加留痕："初判 X → 面试官裁定 Y，理由：…"。*

**速判：**

- **最大长处：** *一句话点出候选人最突出的强项 + 证据*
- **最大短处：** *一句话点出候选人最致命的弱项 + 证据*

### 优点

- *具体优点 1 + 证据（引用原话）*
- *具体优点 2 + 证据*
- ...

*（如无突出优点，写 "无突出亮点"，不要编造）*

### 待提升点

- *具体待提升点 1 + 证据*
- ...

### 风险点

- *具体风险点 1（如：简历夸大嫌疑、核心原理答错、项目贡献边界不清等）+ 证据*
- ...

*（如无明显风险，写 "无"）*

### 后续面试重点关注

- *下一轮需深挖的点 1（给出具体追问方向）*
- *下一轮需深挖的点 2*
- ...

## 面试记录

### 个人情况

*学历、毕业院校、当前公司、当前岗位。只写简历/自述里明确出现的信息，不推测未明确提及的内容（如年龄、工作年限等），未覆盖的字段写 "未覆盖"。*

### 工作情况

**换工作原因：** *候选人自述；未覆盖则写 "未覆盖"*

**岗位诉求：** *候选人对新岗位的诉求；未覆盖则写 "未覆盖"*

### 问我的问题

*候选人问面试官的问题，按提问顺序列出。未提问则写 "无"。*

### 项目

#### 项目1：*项目名*

- **背景：** *业务背景、团队背景、项目启动原因*
- **产品功能：** *这个产品/系统对外提供什么能力*
- **产品指标：** *量级、QPS、日活、数据规模等；未覆盖写 "未覆盖"*
- **技术：** *关键技术选型 + 候选人在其中做了什么 + 追问时的表现*

#### 项目2：*项目名*

（同上结构）

*（有几个项目写几个，未覆盖的字段明确写 "未覆盖"）*

### 编程题

*题目描述（题面 + 示例用例）。写 "本轮未考" 之前必须先回 `asr.md` 扫过编程题信号（`算法题`/`看一个题`/`共享一下`/`编程题`）——探针 `coding=no` 只代表没有平台代码产物，屏幕共享/白板/口述出题都不会产生卡片（实测漏判 2/2）。*
*形态标注：写代码+自测 / 写代码+零自测 / 只口述 / 靠面试官点破 / **未取样（时间不足）**（见「传统算法/编程题专项评估」）。*
*⚠️ 若形态是"未取样（时间不足）"（面试官明说来不及写、只剩几分钟、环节被砍）：技术深度维度**留空**，本节如实记录已观察到的信号但**注明不作为判分依据**，并把"补一道题、留足 X 分钟"写进「后续面试重点关注」。*
*若有 `candidate-code.<ext>` 与 `coding-analysis.md`，此处写结论，逐行审查与实测记录放到 `coding-analysis.md`，并在此引用。*

**候选人解法：** *思路、代码质量、复杂度、边界处理；实现的算法是否与口述一致。*

**实测结果：** *用题面用例实跑的结论（如"用例 1 期望 True 实际 False"）；若构造了反例，写明。无代码则写"仅口述，无代码可测"。*

**评价：** *独立收敛程度（自己做出 / 卡住 / 面试官点破）、正确性、自我验证习惯、与资历期望的差距。*
````

# monitoring-loop：定期巡检 + 告警

两件事：(A) 用 `/loop` 让 Claude 周期性巡检看板/日志并分析异常；(B) 用 Logfire alert 做服务端常驻告警。两者互补——alert 负责 7×24 兜底通知，/loop 巡检负责带上下文的主动分析。

## A. 用 /loop 做周期巡检

`/loop` 是 Claude Code skill，按固定间隔重复跑一个 prompt 或 slash 命令：

```
/loop 10m <巡检 prompt 或 /slash 命令>
```

- 间隔写法：`5m` / `10m` / `30m` / `1h`，默认 10m。
- 适合：盯部署、盯成功率、周期性扫新 5xx/告警。
- **不要**用于一次性任务。
- 巡检 prompt 要**自包含**（每轮是独立上下文）：写清查什么、基线是多少、发现异常怎么深挖、产出什么。
- **载体选择：跨天/长挂的盯守默认做成独立定时任务 + 消息推送，不要占着交互 session**。session 内 `/loop` 只适合短时、需要当前对话上下文的盯守；凡是要挂几小时以上、或用户还要在这个 session 里继续跟进别的问题的，改成独立 cron（每轮自包含 prompt + 脚本），结论通过消息推送给用户：正常静默或一行小结，异常发普通消息，重大问题走加急电话。用户的纠偏形态高度一致——同一天在多个 session 里分别说「把这个盯守挪到单独的 session / 做成 cronjob + 发消息，有问题打加急电话，不要占着这个 session 了，这个 session 我要用来跟进问题」。被这样说过一次，之后所有盯守类需求都默认走独立 cron，不再在交互 session 里循环。周期巡检的报告落地也要顺手定好：每轮单独一份文档、一份总索引把各轮串起来，并汇总「新发现 / 历史遗留 / 已解决」三类问题，用户翻总索引就能看全貌。

### 可直接用的巡检 prompt 模板

```
巡检 tipsy 生产可观测性（最近 30 分钟，deployment_environment='prod'）：
1. 用 query_run 统计 5xx 与异常：按 http_route / span_name 分组计数（带 LIMIT）。
2. 用 alert_list 看 5 条规则的 last_run / has_matches；对 has_matches=true 的用 alert_history(filter_matches=true) 拉触发明细。
3. 与基线对比（基线见下）。只报「新增 / 超基线 / 首次出现」的异常，自愈/已知良性的一句话带过。
4. 对每个真异常：捞 1 条代表性 trace_id，按 trace 下钻到应用层错误（attributes->>'error' / exception），给出疑似根因 + 是否需要人工介入。
5. 产出：一段简报（健康/警示/事故三态分类），每条结论附 trace_id 与计数。无异常就回「✅ 正常，关键指标在基线内」。
```

基线（随项目演进更新，写进巡检 prompt 里）：
- prod 整体 2xx ≈ 99.8%，全程应 0 个未自愈 5xx。
- 已知良性：偶发瞬态 5xx 自愈、探针打 test web `/` 长期 500、sunrise timeout 偶发降级（良性）。
- 判据：**多接口同刻 5xx + QueuePool exception = 共享连接池打满**（非单接口 bug）；**审核类 403 看 audit.rejected 日志不看 span**。

### 上线后盯盘：先高频、稳定后降频、异常即回滚

用户在密集上线期常要求「上线后密切观测，有问题立即回滚」。这类巡检 /loop 与常规巡检有三点不同，写 prompt 时要落进去：

- **三段式频率（用户常规诉求，作为默认口径）**：这是用户反复要求「写进 memory、后续每次观测都按这个标准执行」的通用节奏，没有特别指定时就按它来：(1) **发布期** 5 分钟一次；(2) **发布完成后** 10 分钟一次；(3) 发布后满 **2 小时**观察期无异常 → 降到 **1 小时**一次，持续到**发布后 24 小时**，全程无问题即主动结束观测。频率切换与结束时机写进 prompt 自己算——记录「上线时刻」，每轮对照当前处于哪一段、是否已到 24h 终点，到点就收尾，别让用户手动改也别无限期挂着。用户如给了别的频率就以用户为准，但缺省一律套这套。
- **锚定这次改动**：巡检对象不是「整体健康」而是「这个 PR / 这次改动引入的信号」。prompt 里带上改动涉及的关键词 / 新增日志关键词 / 相关 route，优先盯它们的错误率与新出现的异常模式，而不是泛泛看全局 5xx。
- **回滚就绪**：发现锚定信号异常时，动作是「立即告警 + 给回滚依据」，不是等分析透。prompt 里预置回滚判据（如「该改动相关错误从 0 涨到 N / 出现某关键词日志」）与回滚手法（关开关 / 回退版本），命中即通知用户并附回滚指令，把「要不要回滚」的决策留给用户但把依据备齐。

配套：带开关（feature flag）的上线，「关开关」通常比「回退部署」更快更可逆，优先作为一线止血手段；巡检 prompt 里点明该改动的开关名与关闭方式。

### 开闸（feature flag）前的三道核验

带开关的功能，「开闸」这一步自身要过核验，不能默认「代码合了、开关一拨就行」：

1. **开关背后的代码真的在线上吗**：开闸把某条链路激活，前提是保护/消费该链路的代码已在运行镜像里。合入 ≠ 部署（见下方三问），更隐蔽的是**反向错配**——开关先开了、配套保护代码还没上：危险路径被激活且无兜底，比「代码上了开关没开」（只是没生效）严重得多。开闸前用运行侧证据核实：运行镜像里能 grep 到新符号 / 新日志关键词、或目标版本已滚动完成。「相关 PR 已合」不算数——同一批 PR 里可能只有外围改动进了主干，核心保护那只还 OPEN。
2. **拦截型开关必须走 shadow → 溯源 → 灰度 → 全量**：先以 shadow 模式记录「若开启将拦截/丢弃什么」；转 enforce 前对命中量**抽样溯源定性**——命中的是垃圾还是真实业务？比例小 ≠ 可开：百分之几的「缺字段」可能全是正常业务因上游 bug 静默缺标，enforce 一开就是每小时误杀成千条。影响面按**绝对量/时段 + 波动区间**报，不只报平均比例；命中含真实业务就先堵上游漏口，enforce 排后。
3. **多环境开关分别核**：pre/prod 的开关是独立状态，pre 验证通过不代表 prod 同状态；给结论时注明「在哪个环境、开关处于什么状态下」得出。踩过：排查半天行为不符，最后发现 pre 环境开关根本没开。

### 部署验收 ≠ 行为生效：带开关上线的盯盘分两层

真实翻车：用户说「代码上线了，帮我盯一下」，盯盘按常规跑起来了，最后是**用户自己**去实锤了「几个开关线上全关（下发值为空串），现在跑的还是改动前行为」并替 Claude 核完部署层验收才把流程推进下去。带开关的上线，盯盘结论必须区分两层，第 0 步先定当前处于哪一层：

- **第 0 步实锤开关运行时状态**：读线上实际下发的开关值（空 / 缺省 = 全关），不许从「代码已合入 / 已部署」推断「行为已生效」。每轮盯盘结论开头声明**当前观测的是哪套行为**（改动前 / 部分生效 / 全量生效）。
- **全关期的观测只能验收部署层**：迁移与启动无报错、新增守卫 / 兜底路径以极低量级健康运行且没有走到危险分支、无新增异常日志。这一层干净的结论上限是「**部署无害**」——此时指标平稳只说明带着关死的开关上线没把线上弄坏，**不许写成「修复生效 / 上线平稳」**，因为跑的还是旧行为。
- **多开关阶梯开闸**：一次只开一个，开前后各记录一次开关状态与锚定指标基线，每阶留出观测窗再开下一个。用户指定某项先不开（部分生效）时，明确报出「已生效 / 未生效修复集合」，并答清未开项对应的问题**仍会存在**、以及它与已开项有没有耦合（互相配套的修复只开一半会不会产生新行为）。
- **依赖先行是 checklist 自带项**：开关背后代码依赖的表结构 / 数据迁移必须在开闸前完成并验证。「要不要先更新表结构」应由盯盘方在开闸计划里主动核掉，而不是等用户提醒。

### 阶梯放量盯守：每档给「放行判定」，播报结论先行

带流量比例开关的功能上线，用户会分档放量（如 0.1% → 0.5% → 2% → 10%），每档都要问同样三件事：「现在怎么样？有什么问题？可以扩量吗？」。真实翻车形态（同一条放量线上两天里出现四次）：cron 播报把十几行原始计数（各类请求数、错误数、每个模型的成功数、基线值）原样推给用户，用户回「简化通知内容」；播报里写「⚠️ 某错误来源超基线，需人工看一眼是不是这次改动引入」，把该由盯守方做的判读推回给用户，用户只能把整段贴回来问「这是什么问题」；一份分析把评审推翻的旧结论、修正表、口径修复混在一起交出去，用户回「你的这些分析我没太看明白。结论是什么？有什么风险？我放到千分之五会有什么问题？」；到了下一档的观察窗终点没有主动给判定，用户来问「总结一下数据，支不支持进一步放量」。规矩：

1. **放量前把每档的通过标准写进 runbook**：每个模型 / 链路的最小成功样本数、通道类硬失败上限（权限 / 未开通 / 限流 / 超时，与内容审核拦截分开计）、时延 p95 相对老通道的上限、最短观察时长、必须验过的形态（流式 / 非流式 / 工具调用 / 无兜底链路）。判定只对照这张表：「这一档没出错」不等于「验证通过」——没出错只说明这几十个用户、这几个模型在这几小时里没撞上问题，通过是每条标准都有样本支撑。标准没满足而用户仍要升档，记成「用户知情豁免（豁免了哪几条、到什么时候补）」，不改写成通过。
2. **每档观察窗到点主动给放行判定，不等用户问**：判定三态——支持下一档 / 继续观察（差什么样本或时长）/ 建议回滚（触发了哪条）；后面跟通过标准逐条 ✅/❌ 对照表、建议的下一档值与升档前置动作、用户需要做的一件事。用户开口问「可以扩量吗 / 支不支持放量」才给，说明播报节奏漏掉了这一档的终点。
3. **回答「升到 X% 会有什么问题」的固定结构**：结论一句话（能不能升、算不算门禁放行）→ 本档验了什么、没验什么（没验的留到哪一档补）→ 风险分三档：基本不会发生的（为什么，靠什么信号兜着）、可能发生但后果可控的（影响多少请求、用户看到什么、止损动作是哪一步）、这一档验不了必须留到后面的 → 升档后盯守方自己接下来做什么。评审复核表、口径修正、旧结论撤回不要混进这段，放附录。
4. **播报（人工或 cron）第一行是结论，后面最多五行关键数字，明细进日志文件**：结论只有「正常 / 可升 / 需回滚」三种写法各加一句原因；每个数字带对照（基线、老通道同口径、放量倍数预期）；用分级前缀——🔴 加急且消息里直接写处置动作（如「改回 0」）、⚠️ 普通消息、ℹ️ 正常静默或一行小结。**判读不外包**：脚本报得出「超基线」就要报得出「是不是本次改动面内的文件 / 是不是存量噪音」，报不出的项由盯守方收到后先核再转述结论；「需人工看一眼」「请确认是否与本次改动相关」这类句子不许出现在推给用户的消息里。存量噪音（长期存在的错误来源、瞬时抖动）核实一次后进白名单只记日志，不再打 ⚠️。
5. **每档先核量级再谈健康**：新档走新通道的请求速率应 ≈ 上一档 × 放量倍数；对不上先查分流配置（生效面、比例键、分桶口径）再看错误率，否则拿到的是错误分母下的健康结论。

### 长时盯盘的生命周期与通知分级

密集上线期的盯盘 /loop 常要挂好几天，两件事必须在**启动那一轮**就交代清楚，别等用户来问：

- **主动报出到期时间**：周期任务有存活上限（Claude Code 的 recurring 循环会在若干天后自动收尾）。启动时就把「到期时刻 + 到期后如何续」写进第一条回复，并在临近到期时主动提醒续期。用户问「这个 loop 什么时候过期」时才去查，说明交代漏了。
- **通知级别要和用户的注意力通道对齐**：普通消息容易被划过去，真需要立刻处置的才走加急通道（电话 / 加急卡片）。启动前先和用户约定分级判据——哪些条件走加急、哪些只发普通消息——并在每条通知开头标级别。真实反馈：用户收到普通消息级的 warning 没在意，回头确认「保持 warning 就行」；**级别的升降由用户定，不要自己悄悄升级成加急、也不要把该加急的降成普通**。
- **「稍后复查」一律直接挂定时器，不要征询**：盯盘里最常见的中间态是「当前还没观测到预期变化，需要过一会儿再看一次」。这时正确动作是**当场建一个定时复查任务并说明它何时触发、会检查什么**，不是回一句「要不要我十分钟后再看一次」。用户为此纠偏过两次，原话形态是「后面如果遇到没有观测到预期情况、需要 10 分钟后复查一次的状况，你就直接起一个定时任务，不要再问我了，因为你问我，我一定会回答你『10 分钟后自动复查』」，以及「这种每天挂一次定时探针的请求你直接做就好了，不要问我」。同类免征询的动作：周期性探针、到期回收检查、长任务的接续唤醒。仍需征询的只有不可逆或对外的动作（删规则、改线上开关、发对外通知）。
- **中途被问要能自证存活与进展**：长挂的盯盘，用户隔天必然回来问「这个 loop 还在跑吗 / 在做什么 / 现在怎么样了」。答这类问题一次给全：巡检目标一句话、当前处于哪个频率段、已执行轮数、最近一轮的时间与结论、下次触发时刻、距到期还有多久——答不出任何一项都等于让用户怀疑任务已经死了。跨天盯盘按天主动发一条阶段小结（过去 24h 跑了几轮、异常几条、当前段位），别让用户靠追问确认任务还活着。另外 session 级 /loop 随会话中断静默消失，恢复会话后第一件事核实巡检是否还在，不在就重建并说明断档窗口。

### 「修了但指标没跌」的分诊顺序

修复上线后，用户会盯着某个面板问「这个指标怎么还没跌到 0」。别急着说修复无效，按序排除三类假象，再谈真失效：

1. **改动还没真正生效**：只改配置不改代码的场景，配置往往要重启 / 滚动发布才加载完；滚动期间新旧实例并存，旧实例仍在产出老信号。先确认发布完成、实例版本一致，再看指标。
2. **窗口与口径滞后**：面板是滑动窗口（如 /h、24h 累计）时，修复后仍会带着窗口内的历史命中往前滚一段；速率类面板要等一个完整窗口才见真值。看「修复时刻之后新增的计数」，不是看窗口总量。
3. **同名信号多个来源**：同一关键词可能被多条链路产出，只修了其中一条。按来源维度拆开计数，确认残留来自哪条未修的路径。

三条都排除后仍不跌，才是修复没覆盖到真实路径，回 `rca-trace.md` 重新下钻。

### 「已有的修复能解决这条告警吗」——三问，别顺口答能

告警响起时用户常追问「之前那个修复 PR / 刚合的那个改动能不能解决这个问题」。这是一个需要论证的判断，按序答清三问，任一不成立就不要说「能解决」：

1. **改动到线上了吗**：合入 ≠ 部署，部署 ≠ 全量实例加载完（滚动期新旧并存）。先确认部署状态与实例版本，再谈效果；只合未部署时，答案是「修了但还没上，所以现在仍会复现」。
2. **修的是不是同一机制**：把告警的触发机制和改动的修复机制摆在一起逐层比对——同一函数、同一失败路径、同一触发条件才算命中。同一模块、同一关键词、症状相似都不够。修的是另一条路径时，说清「不解决，理由是机制不同」并给出仍需的动作。
3. **会不会引入新问题**：用户会追一句「能解决今天的问题，会引入其他新问题吗，你反思清楚」。答清改动的副作用面（超时/重试语义变化、兜底路径是否仍可用、上游依赖变化），以及回滚手法。

顺带把止损与根治分开报：先给**立即止损**动作（关开关 / 重启实例 / 切备用依赖，注明这是止损不是修复），再给根治所依赖的改动与上线时机。用户先问的往往是「如何快速止损」。

### 计数在涨 ≠ 劣化；选信号优先选比例类

看板某条曲线在涨，用户会问「为什么，正常吗」。先归一化再判断：绝对计数会随流量、样本量、覆盖面同步涨，**分子分母一起看**（错误数/请求数、超时数/调用数），比例平稳就属于放量而非劣化；同时确认口径没变（新增埋点、采样率调整、新链路接入都会让计数阶跃）。确实是比例劣化，才进 `rca-trace.md`。

由此推论：要把一个现象做成常驻告警时，**同样的现象优先取比例口径而不是计数口径**——比例对流量波动免疫，阈值稳定、噪音最小，不需要随业务增长反复上调阈值。用户提过一模一样的偏好（「把某降级路径的占比做成告警，噪音最小」）。计数类只适合「正常应为 0」的事件型条件。

**比例口径的反例：分子含无关成分时会被流量构成污染**。比例免疫的是流量**大小**波动，不免疫流量**构成**变化。真实翻车：用「非历史部分占窗口比 ≥ 阈值」盯「留给对话历史的预算被挤压」，但分子里混着与被保护对象无关的固定开销（重配置用户这部分天然大）——重开销用户占比高的时段该比例天天越线，而历史预算实际健康、下游零失败，纯属流量构成噪音。判读比例告警疑似误报时第一问就是**分子里都有什么**；修法不是继续调阈值，而是换口径：直接量**留给被保护对象的绝对余量**（如「中位请求留给历史的 token 数 < N」），阈值取「低于它才真的产生用户可感损失」的物理意义值。换口径前用近几天窗口做**新旧口径触发对比回测**——旧口径命中的窗口逐个定性真伪，确认新口径保住全部真问题窗口、滤掉噪音窗口，再切换。

另外，报一条告警时顺带答清它的**常驻覆盖面**：这条信号有没有对应的长期看板可看、有没有常驻告警规则兜底。用户拿到告警后必然追问「有看板吗、有告警规则吗」——没有就直接给出补建议，别让用户再问一轮。

### 巡检铁律

- **别只盯 ERROR（level 17）**：很多失败是 INFO/WARN 级或 200 流内的应用层失败（如 SSE 端点失败裹在 200 里），按**行为特征**查（如 `POST 时延异常`、`agent run 轮数`），不要只 `WHERE level=17`。
- **瞬态自愈 ≠ 事故**：撞了一下立刻恢复、不复发的，归「良性」，别拉响警报。
- **新异常才深挖**：每轮先和基线 diff，把精力放在新增/超阈值的，避免重复分析同一已知项。
- **分词型日志库的关键词计数先精确过滤再引用**：巡检里凡是靠"搜一句报错短语数命中"得到的数字（尤其是全文检索型日志库，引号短语按切词 AND 匹配而非短语匹配），必须同时算出分词命中与 `content like '%原短语%'` 精确命中两个数，**只引精确数**；巡检脚本对多词短语禁止裸 `count()`，统一走返回两个数的封装。踩过：一条巡检告警把某服务 1700 多条"数据库连接中断"报成主链路故障，精确匹配 0 条——命中全是另一接口打进日志的大段英文文本凑齐了那几个普通词；同坑两个月复犯 ≥7 次，因为它一直被写成"常见坑"而不是查询模板的默认形态。完整门禁见 bug 排查类 skill 的 investigation-discipline「分词型日志库的关键词计数门禁」。

### 巡检/审计的覆盖面要有分母：以「有真实流量的组件全集」清点

例行巡检、资源审计这类「扫一遍看有没有风险」的任务，完整性不能用「检查项全绿」自证——检查项只覆盖**已接入巡检的**组件。用户的验收追问形态是固定的：「你扫描了哪些？还有哪些没有扫描？」「还有 N 个有真实流量的组件从没审计过，继续扫」。答不出未覆盖清单，等于覆盖率未知。规矩：

1. **分母 = 有真实流量的组件全集**：先按真实流量/调用量枚举全部在用组件（不按「接了统一监控的」为准——没接监控的恰恰是最危险的分母成员），再逐个标注：扫没扫、用什么数据源扫。
2. **单一数据源查无数据 ≠ 全绿**：某组件在统一监控面取不到指标时，那是**观测盲区不是健康**，要下钻到该组件自身的产品级监控/日志通道补数；补不到的显式列入盲区清单并写明「要补齐得走什么通道」，不许把盲区当绿灯略过。昨天有数据、今天变无数据的检查项，按新风险报而不是静默跳过。
3. **报告固定带三个数**：已覆盖组件数 / 未覆盖组件清单 / 盲区项清单。三者常态化出现在每轮巡检报告里，覆盖缺口才会被持续追赶，而不是等用户回头清点。

## B. Logfire alert（服务端常驻告警）

### 一条告警进来先定位「哪个平台 + 哪个服务」，别顺着上一轮的语境答

真实翻车：用户问「连接池告警是哪个服务的？我看是某个前端向的服务，你好好分析清楚」，本轮先去翻了另一个监控平台，找到一条名字最像的连接池规则、论证它属于另一个服务，还反过来说用户的直觉对不上；用户回了一句「我说的是这个告警」并贴出原始卡片，才发现那是**另一个平台的另一条规则**，用户的直觉从头到尾是对的。教训是：告警归属必须从**用户手上那张卡片**反查，不能凭名字相似或上一轮的语境猜。

拿到一条告警先定这三项，再谈根因：

1. **哪个平台**：应用层 telemetry 还是基础设施指标（边界见 SKILL.md）。同一个现象（连接池打满、时延升高）在两个平台上常各有一条名字很像的规则，答错平台等于整轮排查都在查另一件事。卡片里的项目名、规则链接域名、指标名形态（应用 telemetry 的 span/异常类型 vs Prometheus 指标名）都能定平台。
2. **哪条规则**：用卡片里的规则 id / 链接直接取那条规则的定义，不要按名字在规则库里搜"最像的一条"。用户说「就是这个告警」时，唯一权威是他贴的那条链接。
3. **哪个服务**：从规则定义与命中明细里的**路由/服务标签/指标标签**判定，不从代号或看板目录名推断。内部服务常有代号，代号与服务名的映射记错就会把归属整体搞反。

用户凭直觉给出的归属（「我咋看是某某服务的」）**先当作待验证的强线索而不是待纠正的错误**：他看的是原始卡片，你看的可能是错的那条规则。要否定用户的判断，先出示"我看的是哪条规则、它的服务标签是什么"，并主动问一句「你看到的那条在哪儿？发我我再核」，而不是直接下"跟它无关"的结论。

### 查历史窗口的告警：时间范围要用工具参数传，别只写在 SQL 里

告警卡片里的时刻通常是几小时前，而查询工具默认只看**最近 30 分钟**——SQL 的 `WHERE` 时间条件与这个默认窗口取**交集**，不会把窗口撑开。踩过：按卡片时刻写好 SQL 却返回空结果，误以为"数据没了/口径错了"，实际是两个窗口交集为空。查历史窗口时必须把起止时刻通过工具的时间参数传进去，`WHERE` 里的时间条件只是二次收窄。

### 告警时刻与用户手机上的时间不一致：先答时区，别当成告警延迟

用户会问「这条告警我这边是晚上 9 点收到的，你给的时刻差了 8 小时，是时区问题吗」。答案基本都是：**告警原文与查询结果用 UTC，用户的通知渠道按本地时区展示**，差值就是时区偏移，不是告警延迟或时钟漂移。规则：

- 报时刻**一律双写**：`UTC 时刻（本地时刻）`，别只给一个让用户自己换算。跨时区对齐错一次，整段时间线的因果顺序都会读反。
- 差值恰好等于本地时区偏移（且不随时间变化）→ 判时区展示差异；差值不规整或在变化 → 才去查数据延迟/评估水位/时钟问题。
- 定位窗口、拼查询、写结论里的时间线时统一用 UTC 做内部口径，只在给用户看的那一层加本地时刻括注。

### 根因链要一路追到上游，别停在"直接死因"

同一次事故里的现象层次常是：读接口超时（症状）→ 共享连接池被抽干（直接死因）→ 写侧 handler 在等上游期间一直持有连接（机制）→ 上游依赖变慢到几十上百秒（触发源）。只报到"连接池打满"就给"扩池"的建议，会把治标当治本——上游再慢一次，扩过的池子照样被填满。

- **看请求量再定性质**：流量没涨而错误齐爆 = **延迟事件**不是流量事件，此时扩容类建议一律降级为治标，重点转向"谁把资源占住了"。
- **顺着最慢的那层往上找**：把同窗口内各层的时延分位摆开（入口路由 / 内部调用 / 外部依赖），最慢的那层就是下一跳。慢查询为空却整体很慢，说明卡在非 DB 的外部等待上。
- **结论分三档给**：治本（改掉"跨外部调用持有稀缺资源"这类结构问题，按规矩带上观测）、治标（扩容/调参，注明扛不住极端情况）、上游侧（超时与降级，别让单个外部请求挂几分钟）。用户要的是这三档，而不是只有一条建议。
- 多路由同刻齐爆是**共享资源**被打满的签名，不是某个接口的 bug——别按单接口去查代码。

### 读告警 = 读 Logfire，不是读飞书群

飞书告警群**读不到原文**（webhook bot 发的卡片，OpenAPI 历史消息接口返回空；`search:message` scope 被禁）。用户说「读报警群/分析最新告警」时，真正的源头是 Logfire：

- `alert_list(project="tipsy")` → 所有规则 + 每条的 `last_run` / `has_matches` / `has_errors`。
- `alert_history(alert_id=<uuid>, filter_matches=true, start_timestamp=, end_timestamp=)` → 某规则的历次触发明细。

### alert 规则的结构（建/改告警时照抄）

`alert_create` / `alert_update` 的核心字段：

| 字段 | 含义 | 例 |
|---|---|---|
| `name` | 规则名（建议带 `[P0]`/`[P1]`/`[P2]` 前缀） | `[P1] newapi 渠道缺失 503` |
| `description` | 写清：盯什么、口径、正常基线、命中后怎么处置 | 见现有规则，描述里就把 runbook 写进去 |
| `query` | SELECT；**用聚合 + `HAVING/WHERE total>=N` 过滤孤立偶发**，避免单条噪声刷屏 | 见下 |
| `time_window` | 评估窗口（ISO 8601 duration） | `PT1H` / `PT10M` / `P1D` |
| `frequency` | 多久评估一次 | `PT15M` / `PT10M` / `PT1H` |
| `watermark` | 数据延迟补偿 | `PT1M` |
| `notify_when` | 按条件形态选,见下方设计要点 | `has_matches` / `starts_having_matches` |
| `channels` | 通知渠道（飞书 webhook 已配，复用现有 channel id） | `0e41be0c-...` |
| `environments` | 限定环境，空=全部（规则里多在 query 内写 `='prod'`） | `[]` |

设计要点：
- **错误文本要多字段兜底，别赌错误只落在一个列里**：同一类失败在不同链路里可能记在不同字段——有的进 `exception_message`，有的裹在 `message` 里，有的塞进 `attributes->>'error'`。告警 query 只 `LIKE` 其中一个字段，就会把记在其它字段里的命中整批漏掉。真实翻车：一条 P0 只查 `exception_message/message`、还用 `span_name LIKE 'chat %'` 收窄，结果连续两天的命中（记在 `attributes->>'error'`、且来自另一条 request chain）全部静默漏报。修法是对错误文本做 `coalesce(exception_message, message, attributes->>'error')` 再匹配，并按 trace 关联 `request_path` 区分链路，不要用 `span_name` 前缀把范围提前焊死。
- **过滤条件宁可宽一档再靠聚合收敛**：能定位对象的维度（route / chain / model）放进 `GROUP BY` 与结果列，用来事后区分；用来「圈定要不要报」的匹配条件先覆盖全，别用某个只在部分链路成立的前缀/标签当准入闸，否则漏报是静默的、要靠用户回头核口径才发现。
- **window 与 frequency 对齐**（如都 `PT10M`）可避免重复计数/刷屏。
- **`notify_when` 按条件形态选**：突增/事件类条件（正常时 query 无结果）用 `has_matches`；「一旦出现会连续多个窗口持续命中」的**状态类条件**（存量脏数据存在、水位超限、某配置缺失）用 `starts_having_matches`——只在从无到有的边沿报一次，否则每个评估窗口都重发同一条告警轰炸群。要同时感知恢复用 `has_matches_changed`。真实教训：一条状态类告警配成 `has_matches`，配上就每窗口重复报，修法就是改 `notify_when`，而不是反复调阈值。
- query 里**带上命中条数 + 关键维度**（模型名/route/reason），这样飞书卡片正文就有上下文。
- 阈值留余量过滤正常波动（如「7 天约 5 次」就设 1h 内≥3 才报）。

建告警示例（5xx 突增）：

```jsonc
alert_create(
  project = "tipsy",
  name = "[P1] prod 5xx 突增",
  description = "近10分钟 prod 5xx 总数≥10 触发。正常应≈0。命中后按 route 看分布，捞 trace 下钻应用层 error。",
  query = "SELECT http_route AS route, count(*) AS cnt, sum(count(*)) OVER () AS total FROM records WHERE deployment_environment='prod' AND http_response_status_code>=500 GROUP BY http_route HAVING sum(count(*)) OVER () >= 10 ORDER BY cnt DESC",
  time_window = "PT10M",
  frequency = "PT10M",
  watermark = "PT1M",
  notify_when = "has_matches"
)
```

> 改/删告警前先 `alert_list` 拿 id 与现状，跟用户确认再动；`alert_status` 看启停。

### 告警没响 ≠ 没问题：静默失效排查

真实教训：接口连续报错好几天，一条告警都没来——告警链路任何一环坏掉都是**静默的**。用户问「为什么没报警」时按序排查：

1. `alert_list` 看该规则的 `has_errors` / `last_run`：查询自身报错、或 `last_run` 长期停跳，规则等于不存在；
2. 规则是否 `active`（`alert_status`）、channel 是否还挂在规则上——外部凭证轮换、账号/成员变更都可能悄悄打断 webhook 送达；
3. query 口径是否覆盖这类错误（典型漏：报错走 4xx / 应用层日志，规则只盯 5xx span）；
4. **用出事窗口回放**：把规则 query 加上事发的 `start_timestamp/end_timestamp` 手动 `query_run`，理应命中——不命中就是口径问题，命中了则问题在 2/3 环。

**新建/补齐告警后必须双向验证，不许「配完即信」**：正向——用历史出事窗口回放 query 确认能命中；反向——用**正常时段窗口**回放确认平时不命中。「配上即报且每窗口重复报」不是灵敏，是口径把常态当异常、或 `notify_when` 选错（见上方设计要点），先修语义再定阈值精确值。channel 送达有条件就人为触发一次核实。周期巡检（/loop 或每日定时）时顺带体检全部规则的 `has_errors` 与 `last_run` 是否停跳——**告警系统本身也要被监控**。

### 临时告警要有回收生命周期，别沉淀成僵尸规则

为验证一次上线（如「某修复上线后观察双发指纹是否复发」）临时建的观测告警，名字带 `[临时]` 前缀、`description` 里写清**建立目的 + 预期观察窗口 + 达成什么条件就删**。观察期一过就 `alert_delete` 收掉：临时规则长期挂着会在巡检体检里跟正式规则混在一起，误报还占注意力。

**「N 天后再做」的收尾动作必须有落地的触发器，不能只写在文档里**：告警治理常留下一批延期动作——观察 7 天后删掉被替代的旧规则、灰度两周后收紧阈值、临时规则到期回收。把这些写进 `description` 或交接文档只是**备忘**，不是**保证**：没有任何东西会在到期那天叫醒你，会话早就结束了。所以在**约定延期动作的同一轮**就把触发器建好：定时任务（cron）或周期巡检（/loop）里挂一条到期检查，检查项写明「该删哪条规则、按什么判据确认可以删、删不掉时报给谁」。然后把触发器本身的存在、触发时刻、以及它自己的存活上限一起报给用户。用户的追问形态就是「这种 7 天后要做的事情，你是否已经留了 loop 或 cron job，来确保 7 天后这些内容真的会跑起来？」——答不出触发器在哪，等于这批延期动作已经丢了。周期巡检的每轮顺带核一次：有没有已过观察期却还挂着的 `[临时]` 规则。回放这类临时告警时注意区分「修复前已持久化的旧数据回放命中」和「修复后新增命中」——前者是历史残留不代表修复失效，query 里要能把两者分开（如带上时间/checkpoint 维度），否则会把历史误当复发。

### 「让告警别再刷屏」的正确动作分诊

用户说「这个告警一直报，怎么让它报一次就停 / 沉默一段时间」，先分清诉求再动手，别一律去调阈值：

- **配上就每窗口重复报** → 是 `notify_when` 选错（状态类条件配成了 `has_matches`），改成 `starts_having_matches`（只报边沿）或 `has_matches_changed`（要同时感知恢复），见上方设计要点。这是「重复报」的头号病因。
- **确实是真问题、只是想暂时静音（如已知在修）** → 用 `alert_update(active=false)` 停掉、修复后再 `active=true` 恢复，而不是删规则或把阈值调到永不触发（后者会把规则变成静默失效的僵尸）。停用属于对告警的改动，先 `alert_list` 确认现状、跟用户说明再动。
- **常态波动被当异常** → 是阈值/口径问题，按 `quant-decision.md`「观测窗口与覆盖面」先用 `query_run` 查真实 series/基线再定阈值，别拍脑袋加余量。
- **用户说「让它一天只报一次 / 降低频率」→ 先别照字面把 `frequency` 降到 `P1D`**：降频 + 放大窗口是「降瞎」不是「降噪」——一整天样本聚在一起算，某小时的尖刺被全天稀释，大概率永远不过线、把告警做成近乎失效，且真出事最长要等一天才发现。先查这条为什么吵：若**已经是 `has_matches_changed` 却仍连报**，多半是**阈值卡在正常波动区间反复横跳**（指标过线↔不过线每翻转一次就触发一对，正常 p99 本就贴着阈值）。这时根因是**阈值不是频率**：查真实 series，把阈值抬到**正常 p99 之上**（只在真逼近上限/timeout 才响），保持原频率，横跳自然消失且灵敏度不减。用户确实要硬性「每天最多一条」再叠加降频，但要讲明稀释与滞后的代价，别默默降频冒充降噪。改完在 `description` 里记下调整时间与原因方便回溯；并留一句给未来：若指标整体劣化到又贴线，该去查为什么变慢，而不是继续抬阈值。
- **整个级别的告警都没人看** → 这不是单条规则的问题，按下方「按级别做批量治理」处理，别一条条调阈值。
- **级别与实际影响不匹配** → 规则按"机制上有多严重"定级（如"丢弃即永久数据丢失"配 critical），但实际命中的每一次都查下去发现无用户可感影响（量级个位数、下游可重建、已被兜底吸收），这就是错级不是灵敏。用户的反馈很直接：「这种没有实质影响的告警不要烦我了，我要非常低的噪音」。处置不是停用而是**按实际影响重定级 + 加实质性门槛**：把触发条件从"发生过"改成"达到有影响的量级/比例"，级别降到与影响相称的一档，把原来的低量级形态留给看板或日报而不是即时推送。改前先用历史命中回放确认新门槛不会漏掉真事故窗口（正反双向验证，见上文）。定级判据统一按"用户是否可感 + 是否不可逆"两问答，答不出可感影响的一律不配即时推送级。

### 按级别做批量治理：「某一档告警全都没人看」

用户会提出整档诉求而不是单条诉求：「低一档的告警没人看，群里打扰太多，以后只推最高档，低档的要么调严升档、要么废掉」。这是一次**批量重构**，先出方案对齐再动手（用户明确说「我们对齐方案之后再落地」），不要收到诉求就开始逐条改。

方案要按「一条一行」的表交出，每条至少这几列：现有条件与阈值 / 最近一段的实际命中量 / 有没有同现象的高档规则已经覆盖 / 建议处置。处置只有下面三种，每条必须落到其中一种，不许含糊：

1. **有对应高档规则** → 低档那条直接废掉（去重，不是降噪）。先确认两条盯的是**同一机制同一路径**，只是阈值不同；症状相似不算同一条。
2. **无对应高档规则、但调严后够得上高档** → 升档：把阈值提到「达到这个量级确实需要立刻处置」的位置，改成高档推送，原低档那条删掉。阈值不能拍脑袋，用历史 series 反算——新阈值在过去若干天该命中几次、这几次是不是都值得被叫醒。
3. **无对应高档、调严也够不上（本质是"知道就好"）** → 从即时推送里摘掉，落到看板或日报。这类信号不该有推送通道，但也不该直接删规则失去可见性。

批量改完之前先做两件事：**逐条正反回放**（历史出事窗口能命中、正常时段不命中，见上文双向验证）；**把删除清单单独列出来交用户确认**——删规则是不可逆动作，且删掉后那个信号在群里彻底消失，容易在很久以后才被发现漏了。改完给一份前后对照：治理前各档规则数与日均推送条数、治理后的预期值，让降噪效果可被验证而不是感觉。

## 巡检 + 看板 + 告警怎么配合

- **临时盯一件事**（如刚发布、跟一个 bug）→ `/loop` 巡检，灵活、带分析、用完即停。
- **长期固化的健康面**→ 做成 `dashboard-panels.md` 看板，人随时看。
- **要被动收到通知**（不盯屏）→ Logfire alert，webhook 到飞书。
- 三者常一起上：巡检发现新问题 → 建看板长期观察 → 加 alert 兜底通知。

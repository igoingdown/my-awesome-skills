# 候选人评分细则（打分时读）

配合 SKILL.md「评分体系」的档位定义与严格原则使用。本文件是五维判据、AI coding 专项、传统算法/编程题专项、五维→综合分映射的完整展开。

## 六维度定性判断

六个维度：**业务理解、技术支撑、技术广度、技术深度、编码与算法、软素质**

> **为什么把「编码与算法」独立出来（2026-09-08 重构，真实事故驱动）**：原先只有五维，编码结果寄生在「技术深度」里。真实事故：某 4 年 P6 候选人项目侧表现优秀（业务理解/技术支撑/软素质三个 `+`，量化能力与工程自省都有确凿证据），但提交的算法代码实测四个用例全错、含结构性建模错误、零自测。AI 被迫在技术深度这一格里二选一，最后填了 `=` 并在正文写「业务系统扎实与算法全错两者抵消」——**「正负相抵」是规则里不存在的自创算法**。后果是评分表看不出负面证据来源，机械套映射表会得出 3.5~4（三个 `+`、无 `-`），AI 又凭直觉手工改成 3，两头都不对（正确答案是技术深度/编码 `-`、综合 2.5）。根因是**一个符号承载不了同一维度内并存的正负证据**。拆出独立维度 + 下面的证据账本，就是为了让每条证据都有唯一落点。

### 第一步：先记证据，再定符号（禁止直接填符号）

每个维度下先逐条记录证据，每条标一个强度：

| 强度 | 含义 |
|---|---|
| `P` | 正向：达到该岗位/资历的明确期望，有原话或实测支撑 |
| `N1` | 一般负向：局部缺失、单点答不出、非核心小错 |
| `N2` | **硬负向**：实测错误 / 核心概念讲反 / 岗位核心基础答错 / 充分取样后零输出 / 核心模块两次独立追问仍停在概念层 |
| `U` | 未取样：没安排、时间不足、被打断、材料未获得 |

### 第二步：按固定优先级生成维度符号（机械执行，不许绕过）

按顺序判，命中即止：

1. 该维度有任一 `N2` → **`-`**。**不得用同维度的 `P` 抵消，不得写「正负相抵」「两者抵消」「相互折抵」这类表述。**
2. 无 `N2`，但有 ≥2 条**相互独立**的 `N1` → **`-`**
3. 无 `N2`/`N1`，且有 ≥2 个**相互独立取样单元**各自贡献 `P` → **`+`**
4. 有取样但不满足上述任一条 → **`=`**
5. 全部证据均为 `U`（无任何有效取样）→ **留空，写「未考察」**。禁止填 `=`

> 「相互独立取样单元」= 不同项目，或同一项目里不同组件/不同问题类型。**同一组件的连续追问只算 1 个单元。**

> 自查：**我这一格填 `=`，是因为真的持平，还是因为里面同时有好和坏、我不知道填什么？** 后者说明你漏了第 1 条——有 `N2` 就是 `-`。

| 标注 | 含义 |
|------|------|
| `+` | 加分项：该维度有明显亮点，有证据支撑，且来自 ≥2 个独立取样单元 |
| `=` | 持平：有取样，无硬负向，未达加分条件 |
| `-` | 减分项：有硬负向（`N2`），或 ≥2 条独立的一般负向（`N1`） |
| 未考察 | 本轮无任何有效取样 → **留空、不记录**（不要勉强给 `=`） |

### 各维度含义

#### 1. 业务理解

候选人对所做业务的理解深度。

- 核心判断：能否讲清业务目标 → 技术方案的映射
- 是否用业务指标而非单纯技术指标衡量成败
- 是否关心 ROI、成本、SLA
- **后端**：能否讲清接口/系统服务的上游业务、量级、关键 SLO
- **算法**：能否讲清模型优化指标 vs 业务指标的差异、badcase 驱动迭代经验
- **大数据**：能否讲清数据产品的消费方、SLA、数据 → 决策链路

#### 2. 技术支撑

候选人的技术能力能否真正支撑业务目标。

- 核心判断：技术选型的决策链路是否清楚、trade-off 意识、上线后真实表现
- 是否能讲出"为什么不选另一种方案"
- 是否有量级估算习惯
- `-` 红旗：把"我们用 Redis"当成设计题答案；扩展性追问直接卡死

#### 3. 技术广度

候选人技术栈的覆盖面。

- 核心判断：岗位相邻领域是否接触过、能否把不同组件串起来
- **注意**：广度 ≠ 列一堆名词，能讲清每个东西的**适用场景**才算广度
- `-` 红旗：简历列一堆"熟悉 X/Y/Z"，但任意挑一个都说不出和同类的区别

#### 4. 技术深度

候选人在至少一个领域的深度。

- 核心判断：被追问原理时能答到第几层
- 简历上写"精通 / 熟悉 X"是否经得起追问
- 关键区分：是**背答案**还是**真懂**（追问时是否崩溃/绕开/换话题）
- **AI 时代的归属校验**：候选人陈述的技术点，可能是 AI（编程工具/助手）替他写或说的，而非他本人掌握。对其方案里的**关键技术点抽查原理**（如"你用了 Lua，它在这里解决什么？"→ 应答"保证多命令原子性"）。**答不出 → 该技术点不计入其掌握**；若是他**主动提交的方案**却讲不清核心原理，从重处理（接近"答错"而非"没答出"）。
- 区分"没答出"（知识盲区，可接受）vs"答错了"（原理讲反，严重扣分）
- `-` 红旗：把核心概念讲反；简历明确写"精通 X"被问 X 基础原理答不出

##### ⚠️ "概念型选手"识别（八股 vs 实战）

有些候选人看过很多"八股"、能流畅复述概念，但缺乏对关键技术的准确判断与实战落地。**流畅 ≠ 懂**，这类表现最容易被高估。

**触发条件只看可复核的技术事实，不看背景。** 学校、公司、是否海归、口音、语速、是否书面化表达**都不是**触发信号——它们与技术能力无关，把它们当风险先验会产生系统性误判（表达风格差异被当成能力差异）。判定只依据下面 3 条：

1. **堆概念、无技术细节**：问"X 怎么实现的"，只会复述定义/比喻（如"skill 就像训练新员工把过程告诉他""大概几百行吧"），始终落不到具体实现 → 技术深度 `-`。**需至少 2 个相互独立的技术追问都停在概念层**才触发（单次答不上可能是紧张或该点确实没做过），并在报告里写明这 2 次追问分别是什么。
2. **架构理由站不住**：问某个架构决策（如"为什么不用 multi-cluster / 分库分表 / 某方案"），给的理由经不起一句反问就崩（如"原系统本来就是大 key，跟你的改造有什么关系？"→ 候选人承认"没仔细考虑过"）→ 技术支撑 `-`。**列了多个候选方案 ≠ trade-off 加分**，要看理由是否成立。
3. **关键技术答反**：刁钻题问到核心机制，候选人自信答错（如"多个 Agent 能否共用一个 MCP Server？"——正解：**STDIO 是单进程 stdin/stdout 管道，不能多路复用，必须为每个 Agent 起独立 server 实例**；答"共用相同 credential 不会有问题"是把 I/O 复用问题误判成鉴权问题，**答反**）→ 技术深度红旗 `-`，从重。
   - ⚠️ **判"答反"前必须读完整段拉锯**。真实教训：某候选人被问双通路时效性，首句是"不应该出现这种问题，都是同一个数据源"，据此判了"答错"；但回原文发现**他在同一分钟内就自己补了"那其实他那数据就是有延迟"**，并给出了完整正确的方案（以 Redis 为准 + double check + 版本号）。初版只引了首句和末句、漏引中间的自我修正，把"表述路径曲折"误判成"答错"，被外部评审改判上调一档。**引用要覆盖完整对话段，别只挑首末两句。**

**表达问题单独记，不触发技术负项。** "自我介绍漂移、抓不住重点、非结论先行、卡顿"这类只进软素质与「面试官复盘·表达效率」的观察，**不得据此判技术深度/技术支撑 `-`**。别把"信息量大 / 书面化流畅"误读成"结构化"——结构化是结论先行、点出价值与难点，不是话多；但反过来，表达不结构化也不代表技术不行。

**判分铁律**：核心维度（技术深度 / 技术支撑）**在已充分取样的前提下**被追问穿或答反 → 即便其他维度有 `+`，综合 **≤ 2.5 不通过**；前面的 `+` 被实质抵消。诚实承认边界是软素质中性项，**不能**用来把技术硬缺口洗成加分。**判 `+` 前先自问：这个亮点扛住面试官的犀利追问了吗？**

> ⚠️ 铁律的触发前提是"取样充分"。若该维度根本没问到（或只问了 1-2 个边缘问题就换题），走 SKILL.md「证据充分性前置门」留空，**不得**用本铁律压分。另外要区分"大厂分工"与"能力缺陷"：候选人说"这块是数仓/中间件团队做的、我提工单"，在分工细化的大厂属正常协作边界，**不构成技术支撑 `-`**（`-` 的红旗是"把'我们用 Redis'当设计答案""扩展性追问直接卡死"）；它影响的是"负责人含金量"的判断，应记在贡献边界一节，不是技术扣分项。

**岗位细化关注点**：

- **后端**：并发与锁、MySQL 索引/事务/MVCC、缓存一致性、MQ 语义、分布式 CAP
- **算法**：模型原理（loss/优化器/反向传播）、训练/推理工程瓶颈、实验设计与指标体系
- **大数据**：Spark/Flink 执行原理、shuffle、数据倾斜、state/exactly-once、数据建模分层

> **边界**：本维度只评估**项目/原理层面**的深度追问结果。**编码题的一切结果（代码可运行性、算法正确性、实现准确性、自测习惯、复杂度分析）一律记入「编码与算法」维度，不得记入本维度。** 这条边界是硬的——历史事故就是因为编码结果被塞进技术深度，导致同一格里正负证据并存而无法标注。

#### 5. 编码与算法

候选人独立把问题落成正确可运行代码的能力。**本维度独立于技术深度，专门承载编码题结果。**

- 核心判断：**面对陌生问题能否形成解题方向、基础概念是否扎实、分析过程是否在推进**。代码完整写对最好，写不出或有实现小 bug 都可接受
- 传统算法题：以思路、基础、分析过程为主，实现正确性为辅（判据见下文「传统算法/编程题专项评估」，其第一原则优先于形态表）
- AI coding 题：看用 AI 的过程——需求澄清、选型、拆 task、功能+性能测试、review、关键原理归属（判据见下文「AI coding 题专项评估」）
- **先判编码形态（`C0`/`C1`/`C1'`/`C2`/`C3`/`C4`），但形态只描述完成度；符号由分析过程与基础决定**
- `N2` 红旗（只有这三种）：**核心算法概念讲反**；充分取样后**分析过程完全停滞**（零方向零推进）；主动提交的方案原理讲反
- ❌ **不是 `N2`**：代码写不完、实测不通过、索引/边界/判定条件等实现 bug、缺 import、零自测、复杂度推不出闭式
- ⚠️ **本维度是后端/算法/大数据岗的核心维度**，出现 `-` 时综合分 ≤2.5（见映射表）

> **未考察的处理**：若本轮完全没考编码题，或编码环节因时间不足未形成可验收主体（形态 `C0`），本维度**留空**，不记 `-`、不压分，把缺口记面试官账上并写进补测清单。**留空 ≠ 通过**：核心维度留空时综合分上限为 3。

#### 6. 软素质

沟通、学习、价值观、稳定性的综合判断。

- 回答是否结构化（先结论再展开）
- 对追问的反应（积极重组 vs 不耐烦/抵触）
- 跳槽节奏是否合理、对前司是否明显情绪化
- 对"近期学了什么"能否答出有说服力内容
- **工作抽象与自我表达**：能否主动、有重点地讲出自己工作的价值与难点（结论先行 / STAR）。**判定规则：若候选人靠面试官逐层追问才讲出真实工作内容与难点（自己开口讲不出重点、抽象不出价值），此情形不作为软素质减分，但明确不能作为加分项（软素质最高只能 `=`）。** 可交叉看简历是否同样"堆功能、不点价值"。
- **红线**：价值观问题（如对同事的不当评价、歧视言论、"卷同事"当荣誉）→ 直接 `-`，且综合分不得高于 2.5

## AI coding 题专项评估

当本轮编码/设计题是 **AI coding 题**（允许候选人使用任意 AI 编程工具、投屏，面试官扮演产品经理只答非技术问题）时，**评估的是"用 AI 的过程与落地细致度"，不是代码能否跑通**（代码 AI 随时能写）。

### ⚠️ 不能只凭 asr 转写文本判 AI coding 题

转写记录的是"候选人最终说出的话"，其中很可能包含**AI 产出的完整、书面化文本**——这会让候选人显得很强、流程很完整，但**那是 AI 的完整，不是候选人能力的完整**。真实水平藏在屏幕操作过程里（怎么写第一个 prompt、有没有选型、有没有测试、被问才补还是主动做）。**评估必须结合面试官现场观察 / 屏幕过程；遇到转写在编码环节突然变得高度书面化、结构化，更要警惕这是 AI 产出而非本人现场表达，不可因"转写流畅"就给高分。**

### 过程清单（必需项，逐条核对）

任一项缺失，在对应维度如实体现（多为 AI 应用能力、技术广度的待提升，必要时落到技术支撑/技术深度）：

1. **需求澄清**：是否主动挖隐含条件/边界（如是否多机、限流维度、量级、并发要求），还是直接把需求原样扔给 AI 取第一版。
2. **方案选型**：是否对比多方案再决策（如限流的令牌桶 / 漏桶 / 滑动窗口），还是照单全收 AI 给的单一方案、无 trade-off。
3. **过程拆解**：是否先让 AI 出设计 / 拆 Task / 定验证（Verification）Plan，再分块实现，而非一句"帮我写个 X"。
4. **质量保障**：写完是否做**功能测试 + 性能测试**，到可交付状态。
5. **代码 review**：过程中是否对 AI 产出做交叉 code review。
6. **原理归属校验**：对 AI 生成的关键技术点抽查原理（见「技术深度 · AI 时代的归属校验」）。讲不清 → 该技术点不计入其能力；主动提交的方案讲不清核心原理，从重。

### 判分锚点

- **加分（AI 应用是真能力）**：主动澄清隐含条件 + 做方案选型对比 + 先方案后代码 + 主动写功能/性能测试 + 对产出能讲清原理并 review。能"现场驱动 AI 高效逼近一个可交付方案"。
- **地板（不加分）**：把需求交给 AI 让它写出来、能复述"标准 AI 协作流程"，但选型/测试/校验都靠面试官追问才补。
- **减分**：直接扔题不选型、不做测试、被问才改关键设计（如多机）、AI 生成的关键技术点讲不清原理（归属校验失败）。

> 提示：本节与团队既有的"识破不懂装懂要切替代评估"一脉相承——对 AI 产出的关键点追问原理，本质就是一次"归属校验 / 替代评估"，能当场把"AI 替他说的"和"他真懂的"区分开。

## 传统算法/编程题专项评估

当本轮是**传统算法/编程题**（面试官出题、候选人手写代码或口述解法，不允许用 AI）时，用这一节。**评估的是"能否独立收敛到一个正确、可运行的解法"**，与 AI coding 题的"用 AI 的过程"是两套标准，不要混用。

### 先定性：这道题落到了哪一档形态

### 编码形态状态机（先定形态，再定符号；五态互斥，必须且只能命中一个）

> **为什么改成状态机（2026-09-08 重构）**：原形态表用「只剩几分钟」「给了足够时间」这类自然语言描述边界，没有客观阈值，导致同一批材料能被判到相反路径。真实事故：三位候选人做同一道题，一位 12 分钟未写完（被打断）、一位 13 分钟两题零输出、一位 9 分钟写完但实测全错——原规则里「时间不足则留空」与「主动提交实测错则判 `-`」两条**可以同时命中**，且没有优先级，结果三份报告的判法互不一致，其中最严重的一份（写完但全错）反而拿到了比零输出更高的分，出现判分倒挂。

### ⚠️ 先明确：算法题考的是思路、基础、和面对陌生问题的分析过程

**这是本节的第一原则，优先于下面所有形态与实测规则。**

传统算法题的评估重心是：**能不能理解题意 → 能不能从零形成解题方向 → 基础概念是否扎实 → 面对没见过的问题时分析过程是否在推进**。代码能完整写对最好，但**写不出来、或者写出来有一些实现层面的小 bug，都属于可接受范围，不构成判死依据**。

判定时按这个优先级看：

| 观察项 | 权重 | 说明 |
|---|---|---|
| 题意理解 + 独立形成解题方向 | **最高** | 能否自己收敛到可行方向（哪怕是暴力解），有没有主动做可行性预筛 |
| 面对陌生问题的分析过程 | **最高** | 卡住时是停滞还是在推进？能否自己抽象、自己发现问题、自己修正 |
| 基础概念是否扎实 | 高 | 用到的数据结构/算法概念是否讲得对（**讲反才是硬伤，想不起来不是**） |
| 复杂度意识 | 中 | 有没有主动意识到复杂度问题、推导方向对不对（**推不出闭式不算硬伤**） |
| 代码完整性与实现正确性 | **低** | 实现层面的 bug（索引写错、边界漏、缺 import、判定条件写歪）属可接受瑕疵 |
| 自测习惯 | 中 | 如实记录，但**单独不构成判死** |

**只有下面三种情形才算真正的硬负向（`N2`）：**

1. **核心算法概念讲反**（例如把栈说成先进先出、把回溯的剪枝方向说反）——这是基础问题，不是手误。
2. **充分取样后完全没有分析过程**：给足时间与机会，既没有解题方向、也没有推进痕迹（不是"想到暴力解但优化不出来"，而是"完全不知道从哪下手且过程停滞"）。
3. **提交的方案在原理层面讲反**，或声称做过的算法核心讲不出来。

> **实现层面的 bug 一律不判 `N2`。** 索引用错、循环变量写歪、判定条件不对、缺 import、终止条件漏一个分支——这些是"写得不够仔细"，反映的是熟练度与当时的时间压力，不是能力缺陷。**实测结果的作用是精确描述他写到了哪一步，不是用来判死。**

> ⚠️ **历史事故（2026-09-08，本节因此重写）**：我曾把"交付的代码实测全错"直接定为硬负向、判技术深度 `-`、综合压到 2.5。当事候选人（4 年 P6）实际表现是：自己提出整除预筛、手工验算给出正确划分、独立识别回溯方向、主动指出复杂度高、把搜索过程抽象成树并推到 2^n 量级、中途还自己发现"这不是个等差数列"并修正——**分析过程完整且在推进，错的只是 9 分钟里写出来的实现细节（循环变量用了 curIndex 而非 i、判定条件写成了 ans.size()==k）**。用实测结果判死，等于把"考思路"的题变成了"考手速和仔细程度"。这与本文件「AI coding 题专项评估」开篇「评估的是过程，不是代码能否跑通」是同一个取向，两节必须一致。

**判定顺序：先看分析过程与基础（决定基调），再看有没有形成"可验收主体"与实测结果（用于精确描述完成度）。**

「可验收主体」定义：核心函数体成型（有主逻辑与返回路径），审查者补齐环境性缺失（import、main 入口、包声明）后**即可编译运行**。缺 import 属环境性缺失，**不影响**主体成立；缺核心分支、缺返回值、缺递归入口则**不构成**主体。

**形态只用来描述"他走到了哪一步"，符号由「分析过程 + 基础」决定。** 同一形态下，分析过程好坏可以差出两档。

| 形态 | 机械判定条件 | 编码与算法维度 | 综合分影响 |
|---|---|---|---|
| **C0 时间不足未完成** | ①未形成可验收主体；②面试官主动打断或计划时长耗尽（**以"是谁终止的"为准**） | **留空** | 不压分；核心维度留空 → 上限 3。已写代码的错误如实记录，注明"不作判分依据" |
| **C1 充分取样零输出** | ①无代码也无可执行伪代码，**且分析过程停滞**（没有解题方向、没有推进痕迹）；②单次机会 ≥15 分钟或两次合计 ≥10 分钟；③无结构性提示；④非流程性打断 | **`-`**（`N2`） | ≤2.5 |
| **C1' 有分析过程但没落代码** | 达到 C1 的时间阈值，但**形成了解题方向或有明确推进痕迹**（提出可行方向、做了可行性预筛、能手工验算） | `=`；方向正确且推导有质量的可给 `+` | 不压到 ≤2.5 |
| **C2 有主体但实测错** | ①已形成可验收主体；②补齐环境性缺失后实测，用例错误或输出违反契约 | **按分析过程定**：分析过程完整（独立方向 + 基础概念对 + 有推进）→ `=`，实现瑕疵写进风险；分析过程本身有问题或核心概念讲反 → `-` | `=` 时不压分；`-` 时 ≤2.5 |
| **C3 有主体且实测对，但零自测** | 实测全部通过；平台可运行而运行记录为空，且无口头走查 | 最高 `=`，记「自我验证习惯缺失」`N1` | 不因本条压到 ≤2.5 |
| **C4 有主体、实测对、有自测** | 实测通过 + 有运行记录或口头走查 | 可给 `+` | 正常给分 |

**补充规则：**

- **C2 是本次重写的核心**：原来 C2 一律判 `N2`（≤2.5），现改为**看分析过程**。理由见上文事故复盘——"写出来但有实现 bug"和"不会做"是两件完全不同的事，前者最多是熟练度问题。
- **只口述、没落代码**：区分 C1 与 C1'——关键不是有没有代码，而是**有没有分析过程**。
- **靠面试官点破才通**：独立解题能力未达标，本维度**封顶 `=`**，必须写明是提示后才通。
- **复杂度推不出闭式**：记为观察项，不构成 `N1`。推导方向对但没收敛，属正常（尤其在有时间压力时）。

> **判 C1 还是 C1'、C2 判 `=` 还是 `-`，都要回到第一原则：他面对这个没见过的问题，分析过程是在推进还是停滞？** 停滞才是问题，推进但没走完不是。

> **C0 与 C1/C2 必须在报告里区分开，不能都写成"编码未取样"。** C0 是"我们没测到"，C1/C2 是"测到了且没达标"——前者是面试官的流程缺口，后者是候选人的能力证据。混为一谈会让下一轮误读。

> **判 C1/C2 前自查**：这道题是候选人写不出，还是我们没给够时间？看**是谁终止了这个环节**——面试官主动打断且主体未成型 = C0；候选人自己表示没思路、或主体已成型 = C1/C2。

### ⚠️ 必做：把候选人代码真的跑一遍

**只要拿到了 `candidate-code.<ext>`，就必须用题目自带的示例用例实测，不能靠肉眼判断对错。**

**实跑的用途是"精确描述他写到了哪一步"，不是"用来判死"。** 两件事都要做到：

- **不能靠目测下结论**（真实事故：面试官现场说"看着能跑通"，实测是 SyntaxError；另一场说"思路没太大问题"，实测是判定条件写歪）。目测的准确率很低，报告里必须写实测结果而非印象。
- **实测错误不等于能力不行**。实测的价值是让报告能精确写出"他的方向对，但第 N 行的循环变量用错了"，而不是笼统地写"代码有问题"或据此判死。**判分基调回到分析过程与基础，见本节第一原则。**

> 反过来说：如果实测发现代码**完全正确**，那是强正向证据，值得明确写出来。

- 用 node/python/go 等把代码补成可运行片段（去掉 TS 类型、包一层 main），喂题面的每个示例用例，比对期望输出。
- 若怀疑算法层面有反例（如贪心/双指针），**主动构造反例并跑验证**，不要停在"双方都想不出反例所以放行"——想不出反例 ≠ 没有反例。
- 把"实测 X 用例期望 True 实际 False"这类结论写进 `coding-analysis.md`，作为判分的硬证据。

### 审查清单（有代码时逐条核对，写入 coding-analysis.md）

1. **题意转化 / 需求澄清**：是否主动澄清歧义（如"子数组要不要连续""能不能重叠"）、用示例自验证理解、给出可行性剪枝。
2. **问题分解**：主循环/辅助函数拆分是否合理，子问题抽象是否正确。
3. **算法正确性**：算法选型能否覆盖题目全部情况。⚠️ 特别核对**实现的算法与口述的思路是否一致**——真实案例里候选人口述"找任意子集"、代码却写成"找连续窗口"，是两道不同的题。
4. **实现正确性**：边界、off-by-one、越界、类型；以实测结果为准。
5. **完成度**：题目所有要求是否都实现（如"有解要输出一组解"这类附加要求常被漏掉）；脚手架/模板代码（如 `console.log("Hello World!")`）是否清理。
6. **自我验证习惯**：写完有没有跑用例/走查。平台可运行却运行记录为空 → 明确记负向。
7. **复杂度意识**：是否主动分析时间/空间复杂度、自评 TLE 风险。
8. **作答独立性**：结合页面切换记录，中途有无长时间离开（疑似查资料/问 AI）。

### 判分锚点（按资历校准，见「评分体系 · 资历×深度期望」）

> ⚠️ **先跑上面的「编码形态状态机」定形态，形态决定能取的符号，本节只在形态之内做细分。** 形态 `C0`（未形成可验收主体且被面试官打断）→ 维度留空，不走下面任何一档。

- **加分（`+`）**：独立收敛到正确解法 + 落成可运行代码 + 主动自验证 + 复杂度分析到位（形态 C4）。**或者**：面对陌生问题的分析过程质量突出——独立形成方向、自己发现并修正问题、推导有章法，即使代码未完成或有实现瑕疵（C1'/C2 中的高质量情形）。
- **中性/持平（`=`）**：形成了解题方向、基础概念没讲反、分析过程在推进，但代码未完成、或有实现层面的 bug、或实测不通过（C2 默认落这里）；或实测对但零自测（C3）；或靠提示才爬出来（封顶 `=`）。
- **减分（`-`）**：核心算法概念讲反；或充分取样后分析过程完全停滞、零方向零推进（C1）；或主动提交的方案原理讲反。

> **实现 bug 不是判死项。** 索引写错、循环变量用歪、判定条件不对、缺 import、终止条件漏分支——一律按"实现瑕疵"记入风险，不升级为 `N2`。**判 `-` 之前先自问：他是不会分析，还是分析对了但没写仔细？** 后者最多 `=`。

> **关于自测**：零自测如实记录（`N1`），但**不与实测错误叠加判死**。原表述"写完没验证、实测是错的比没写完更严重"已废除——它把"写出来了但不够仔细"排在了"完全不会"之前，与"算法题考思路"的第一原则冲突。

> **与 SKILL.md「资历校准·达不到资历期望即降档」的关系（已统一）**：该条提到高资历候选人"中等算法题写不出"判 `-`。**以本节第一原则为准**：真正触发降档的是"分析过程停滞 + 基础概念讲反"，不是"代码没写对"。高资历只提高对**分析质量与基础扎实度**的期望，不提高对"实现零 bug"的期望。

### 区分"没做出来" vs "做错了" vs "没验证"

- **没做出来**（时间不够、卡在某步）：知识/熟练度问题，按资历判，可接受度较高。
- **做错了**（算法用错、概念讲反）：严重，尤其主动提交的解法。
- **没验证**（有平台不跑、写完不走查）：工程素养问题，无论对错都要如实记；若"没验证"叠加"实测是错的"，从重。

> 提示：中高级岗对"中等题落地一个正确解法"的期望是硬线。口述得再流畅、思路方向再对，**没落到正确可运行代码，就不能当作"这题做出来了"**——这与"广度/流畅不能冒充深度"是同一条反陷阱原则。

## 五维打标 → 综合分 映射（参考）

**核心维度**（后端/算法/大数据岗）：技术支撑、技术深度、**编码与算法**。非核心：业务理解、技术广度、软素质。

**按下列顺序判，命中即止。这是决策表不是权重表——不存在"加减抵消""净额""相抵"这类算法。**

| 顺序 | 条件 | 综合分 |
|---|---|---|
| 1 | 软素质价值观红线 `-`（作弊未反思等） | ≤2.5，且综合不得高于 2.5 |
| 2 | ≥2 个核心维度为 `-` | 2 |
| 3 | 恰好 1 个核心维度为 `-` | **2.5**（**不得因其他维度有 `+` 而上浮**） |
| 4 | 无核心 `-`，但有 ≥3 个维度留空 | **不出分**，写"取样不足，无法给出综合评分" + 补测清单 |
| 5 | 无核心 `-`，有核心维度留空 | 上限 **3**（留空不加分不减分；必须写明留空维度与补测项；**不得给 ≥3+**） |
| 6 | 无核心 `-`、无核心留空，≥2 个非核心 `-` | 2.5 |
| 7 | 无核心 `-`、无核心留空，恰好 1 个非核心 `-` | 上限 3 |
| 8 | 无任何 `-`、无核心留空，≥3 个 `+` 且来自 ≥2 个独立取样单元 | 3.5（六维均有亮点且 ≥3 个维度各有独立证据 → 4） |
| 9 | 无任何 `-`、无核心留空，1~2 个 `+` 且 ≥1 个来自独立取样单元 | 3+（**若全部 `+` 只来自 1 个取样单元 → 上限 3**） |
| 10 | 无任何 `-`、无核心留空，全 `=` | 3 |

**边界情况一律取低档。** 禁止 2.75 / 3.25 / 3.75 等非档位分数。

> ⚠️ **第 3 条是硬门，历史事故就发生在这里**：某候选人三个 `+`（业务理解/技术支撑/软素质）+ 编码 `-`，若按"数 `+` 的个数"会落到第 8 条得 3.5，正确答案是第 3 条的 2.5。**核心维度的硬伤优先于任何数量的正向证据**——项目做得好和交付错误代码是两件独立事实，不互相消解。正向证据仍要如实写进报告供后续参考，但不参与本轮分数上浮。

**含"未考核（留空）"维度时怎么算**（原表只列了 `+`/`=`/`-` 的组合，留空维度如何参与打分曾无定义，导致同一份材料既可能被当成"无负面证据"也可能被保守当成 `-`）：

| 情况 | 处理 |
|---|---|
| 岗位**核心维度**留空（后端/算法/大数据：技术深度、技术支撑任一） | **分数只用已取样维度算**，留空维度既不加分也不减分；概览必须写"X 维度本轮未取样，证据面不完整，建议下一轮补测后终判"；**不得**给 ≥3+（证据不足撑不起通过线），也**不得**因留空而压到 ≤2.5。⚠️ **本条只封分数上限，不封面试官的 3 档裁定权**——落 3 后面试官仍可基于现场体验裁定通过，见下方「⚠️ 分数上限 ≠ 结论上限」 |
| **非核心维度**留空（业务理解/技术广度/软素质之一） | 分数只用已取样维度算，概览注明覆盖率即可，可正常给到 3+ 及以上 |
| 留空 ≥3 个维度 | 材料不足以支撑评价，**不出分**，报告写"取样不足，无法给出综合评分"+ 补测清单 |

注：这是参考映射，不是硬性公式。最终分数必须结合证据强度判断，但**不得违反"严格原则"硬规则与「证据充分性前置门」**。

### ⚠️ 分数上限 ≠ 结论上限（AI 不得用"证据不足"否决面试官的 3 档裁定）

**真实事故**：某校招场（对标 1-2）后端基础零考察、编码零产出，AI 据「核心维度留空不得给 ≥3+」把分数从 3+ 下调为 3——**这一步是对的**。但接着 AI 写了"这里**不做裁定**，因为缺的不是'某个短板可后天补'，而是校招最核心的两项根本没测，应当补测而非裁定"，把结论定成"不通过/待补测"。面试官随后指出：候选人业务有 sense（点破后能自己想清楚）、记忆方向工作扎实、算法题反应快、做事方法有量化验证闭环，**愿意给 3 分通过**。AI 的"不做裁定"是自己加的限制，规则里没有。

**两条硬边界：**

1. **"不得给 ≥3+" 约束的是分数，不是结论。** 3 档裁定权是 `SKILL.md`「通过标准」明文给面试官的独立权力。AI 把分数落到 3 之后，**必须保留裁定路径**，在概览写"打 3，等待/已获面试官裁定"，**不得**自行写成"不做裁定""应当补测而非裁定""证据不足不予通过"。取样不足是**下一轮补测的理由**，不是**本轮否决裁定的理由**。
2. **AI 的观测盲区不能用来否决面试官的现场观测。** AI 只有 ASR 转写 + 简历；反应速度、吸收提示的速度、冲劲、现场紧张程度、是否边想边说——**这些转写里根本不存在**（见 SKILL.md「面试官现场观察可参与裁定」）。用"我没看到足够证据"去否决"面试官现场看到了"，是把自己的信息缺失当成候选人的缺陷。

**判定动作**：写结论前自查一句——**"我是在报告分数，还是在替面试官做裁定？"** 分数由证据定，裁定由面试官定。二者冲突时（如 AI 判 3 默认倾向不通过、面试官裁定通过），**以面试官为准**，并在概览留痕两者的理由。

> 附带一条容易连带犯的错：**"被点破后能自己想清楚"不等于"结论是面试官给的"。** 同一事故里，AI 把候选人 14:18「确实是的」之后**自己举例把价值讲清楚**的整段（举了 iPhone 17/18 对比、联系自身使用体验、自己收口到"初衷是让用户更高效检索"）写成了"候选人只是附和，结论是面试官推出来的"。正确读法：承认之后**是否还有自主输出**——有，就是"吸收提示快"（校招正向信号，不计加分但绝不记负向）；没有、只答"对"，才是"靠面试官喂"。**判这一条必须读完承认之后的整段，不要停在"确实是的"这句。**

> **关于 3 档的裁定**：当五维指向 3+（如 1 个 `+` 其余 `=`）但存在隐性短板（如 AI 应用能力弱、方案选型缺失、关键数据掌控差）把综合压在 3 时，可落 **3**，并由面试官裁定是否通过——若裁定通过，在概览写明"打 3，面试官裁定通过"及理由（如核心维度有真实底子、短板可入职后习得）。**`+` 维度没有自动把综合顶到 3+ 时，要在概览说明是哪些隐性短板拉低了它。**

# 输出文件模板（写报告时读）

每次评估固定产出**两个文件**，均写入 `<人名>/<目标轮目录>/`；本轮有编程题时另加编码产物：

| 文件 | 内容 | 用途 |
|------|------|------|
| `evaluation.md` | 候选人评价（**六维**打标 + 评分 + 面试记录） | **对外交付物——会被整段复制粘贴进公司招聘系统留档** |
| `interviewer-review.md` | 面试官复盘（五维评估 + 做得好/不好 + 改进建议） | 面试官自用，持续改进 |
| `coding-analysis.md`（有编程题时） | 题面 + 审查清单 + 实测结果 + 反例 | 编码环节判分的硬证据（内部） |
| `candidate-code.<ext>`（有代码时） | 候选人代码原文 | 供实跑与逐行审查（内部） |
| `review-log.md`（**有改判时新增**） | 评审与改判的全部过程留痕 | 内部追溯用，**绝不进 evaluation.md** |

## ⚠️ evaluation.md 是对外交付物：零过程性内容（硬规则）

**用户会把 `evaluation.md` 的内容直接贴到公司招聘网站作为正式记录。** 读者是 HR、后续轮面试官、评审委员会——他们要的是"这个候选人怎么样"，不是"这份评价是怎么写出来的"。

**以下内容一律不得出现在 `evaluation.md` 里**（真实事故：三份报告里各有 6-21 行这类内容，用户明确要求全部删掉）：

| 禁止 | 典型措辞 |
|---|---|
| 版本与改判痕迹 | `v1`/`v2`、"初判 X 改为 Y"、"改判说明"、"三次演进"、"~~删除线~~" |
| 评审过程 | "经 CodeX 评审"、"GPT-6 指出"、"外部评审复核后"、"子代理复核" |
| 自我纠错叙事 | "我上一轮的失误"、"我误读了"、"初版写成了…"、"这条我改过头了" |
| 规则援引与元讨论 | "按 skill 前置门"、"按映射表规则"、"违反了硬规则第 N 条"、"不触发铁律" |
| 撤销/保留的记账 | "撤销第三处"、"这条保留"、"下调为"、"从三处改为两处" |
| 内部评分机制 | "取样单元"、"核心维度留空 → 上限 3"、"分数封顶"、"不作判分依据"、"按决策表第 N 条"、"前置门" |

## ⚠️ 面评只写简历里没有的东西（硬规则）

**面评的价值在于"简历看不出来的部分"**：他被追问时答成什么样、哪里说不清、哪些主张站不住、下一轮该问什么。**简历上已有的客观信息不要在面评里复述**——读者手里就有简历，重复只会稀释真正有信息量的内容。

| 不要写 | 为什么 |
|---|---|
| 学历、院校、专业、起止年月 | 简历首屏就是 |
| 届次、应聘岗位、面试轮次与时间 | 招聘系统的字段，不是评价 |
| 当前公司与在职状态（除非本轮问出了新信息） | 简历有；只有"为什么想走""什么时候能到岗"这类**问出来的**才写 |
| 技术栈罗列 | 简历技能栏有；面评要写的是**追问后哪几项立得住** |

**真实事故 2026-09-09**：报告末尾自造了一节「资格信息」表格，把学历、本科、届次、应聘岗位、面试轮次时间全列了一遍，全部来自简历。用户直接指出"这种内容不需要留在面评里，简历都有，面评只需要保留简历没有的内容"。

**同时注意**：模板已明确"不要增加、删除、合并、重命名任何标题"。上述事故里除了「资格信息」，还自造了「关键优势」「主要风险与待核实」「证据边界」「二面建议」四个标题去替代模板的「优点」「风险点」「后续面试重点关注」——**自造标题往往就是塞冗余内容的入口，按模板写就不会有地方放它们。**

**正确做法：写成"当前唯一结论"的样子。** 结论就是结论，证据就是证据，不解释它经历过什么。

- ❌ `技术深度：v1 判 `-`，v2 撤销后改 `=`（LRU 那条经复核不成立）`
- ✅ `技术深度：=`（正文只陈述当前判断依据，不提曾经判过什么）
- ❌ `**v2 修正**：简历技能栏根本没有 ES，v1 写"把 ES 列进技能表"是事实错误`
- ✅ `ES 倒排索引答得粗（14:38…），但简历技能栏未声称掌握 ES（只写"了解 GO、MySQL、Redis"），且 ES 是他否掉的候选方案，严重度有限`

**改判过程要留痕怎么办？** 写进独立的 `review-log.md`，记：改了哪一条、依据的原话、谁提出的、结论怎么变。`evaluation.md` 只呈现终态。

**判分口径的必要说明可以留，但要写成客观事实而非规则援引：**
- ❌ "按 skill 证据充分性前置门，编码未取样不作负向证据"
- ✅ "编码环节因时间不足未能验证（面试官出题时即说明「应该没时间写了」），本轮不作为候选人的能力判断依据"

## 候选人评价模板（evaluation.md）

**严格按**下面的结构输出。所有斜体占位符替换为真实内容。不要增加、删除、合并、重命名任何一级/二级/三级标题。**六维顺序必须是：业务理解 → 技术支撑 → 技术广度 → 技术深度 → 编码与算法 → 软素质**（2026-09-08 起由五维改为六维，「编码与算法」独立成维，不得省略该行）。

````markdown
# 面试评价报告

## 信息汇总

本轮 *N* 面。

**定性判断：**

维度：业务理解、技术支撑、技术广度、技术深度、编码与算法、软素质。
指标：+ 代表加分项、= 代表持平、- 代表减分项，未考核不记录。

| 维度 | 标注 |
|------|------|
| 业务理解 | *+ / = / - 或留空* |
| 技术支撑 | *+ / = / - 或留空* |
| 技术广度 | *+ / = / - 或留空* |
| 技术深度 | *+ / = / - 或留空* |
| 编码与算法 | *+ / = / - 或留空（本轮无编码题或形态 C0 → 留空）* |
| 软素质 | *+ / = / - 或留空* |

> **维度表只放符号，不在表格下方逐维展开依据**——依据统一写在下面的「概览」里（避免同一条证据在表下、概览、优点清单里重复三遍）。
>
> 出现 `-` 时，在概览对应维度那段写明是哪条硬负向（核心概念讲反 / 分析过程停滞 / 原理讲反）。**编码与算法维度不得因"代码写不完、实测不通过、实现 bug、零自测"判 `-`**——见 scoring-rubric「传统算法/编程题专项评估」第一原则。

### 概览

> ⚠️ **概览是全篇最重要的一段——多数读者只读这里。四条硬约束：**
> 1. **结论与校准基准写在同一句话里**，不要分成两句让读者自己拼。格式：`**本轮面试按<岗位><校准基准>校准，综合评分：X，通过/不通过**`
> 2. 🚨 **概览正文（结论句 + 总述 + 速判）合计不超过 200 字，目标 100 字以内。** 每个方面只写最核心的那一条亮点或缺陷，**不带原话、不带时间戳**——那些进下面的「维度依据」。**维度依据不写在概览里**（2026-09-11 修正，见下方事故）。
> 3. **禁止把评分推导过程写进概览**——"证据分布在几个独立取样单元""在 X 和 Y 之间犹豫按严格原则打 X""决策表第几条"这类内容是内部举证，属 `review-log.md`，不进对外交付物。读者要的是结论与理由，不是算法。
> 4. 同一条证据不得在"维度依据 + 优点清单 + 速判"里重复出现三次。速判只给一句话判断，证据留给「维度依据」。
>
> 🚨 **真实事故 2026-09-11（本条因此重写）**：上一版这里写的是"**维度依据集中写在概览里，一个维度一段**"，结果三份报告的概览分别写到 **2230 / 1669 / 1256 字**（超 200 字上限 6-11 倍），单个维度段落最长 449 字。用户原话：**"预览部分每一个环节都写得太长了……概览部分最好不要超过 100 字，最长绝对不要超过 200 字"**，并要求"每一个方面只写最核心的亮点或缺陷"。
>
> **根因不是写作失控，是规则本身自相矛盾**——既要求"概览是给只读一段的人看的"，又要求"每个维度的依据都塞进来"。六个维度各写一段带原话带时间戳，必然突破任何字数上限。**修正：概览只给结论，依据下移到紧随其后的「维度依据」小节。** 想追依据的读者往下翻一屏就有，只读概览的读者 100 字拿到全部结论。

**本轮面试按 *目标岗位（校招须写明对标职级，如"校招，对标 1-2"）* 校准，综合评分：*X*，*通过 / 不通过 / 打 3，等待面试官裁定***

*一段话总述（**60 字以内**）：整体水平相对岗位期望的位置 + 最关键的那一处加分或减分。不列举全部维度，不带原话与时间戳。*

*⚠️ 打 3 且面试官尚未表态时，结论写"打 3，等待面试官裁定"；**不得**写"不做裁定""证据不足不予通过"——裁定权属面试官（见 SKILL.md「通过标准」与 scoring-rubric「分数上限 ≠ 结论上限」）。面试官裁定后在此追加留痕："初判 X → 面试官裁定 Y，理由：…"。*

**速判：**

- **最大长处：** *一句话点出最突出的强项，**不超过 30 字、不带原话***
- **最大短处：** *一句话点出最致命的弱项，**不超过 30 字、不带原话***

### 维度依据

*承接概览：概览只给结论，这里给依据。一个维度一段，`=` 的维度可合并成一段。*

*每段格式：`维度名 标注：<结论性判断>（<原话或实测证据> + 时间戳）`。**每维控制在 150 字以内**，只写支撑该标注的核心证据——一到两条最有力的即可，不要把该维度所有观察都搬过来；细节留给下面的「优点」「待提升点」「风险点」。*

*出现 `-` 时，这一段必须写明是哪条硬负向（核心概念讲反 / 分析过程停滞 / 原理讲反）。*

*本轮未考完的维度（如编码环节被打断）在这里说明形态与原因，并注明不作为对候选人的能力判断。*

### 优点

- *具体优点 1 + 证据（引用原话）*
- *具体优点 2 + 证据*
- ...

*（如无突出优点，写 "无突出亮点"，不要编造）*

### 待提升点

- *具体待提升点 1 + 证据*
- ...

### 风险点

- *具体风险点 1（如：简历夸大嫌疑、核心原理答错、项目贡献边界不清等）+ 证据*
- ...

*（如无明显风险，写 "无"）*

### 后续面试重点关注

- *下一轮需深挖的点 1（给出具体追问方向）*
- *下一轮需深挖的点 2*
- ...
````

## 旁听场专用：观摩笔记模板（interviewer-review.md）

**用户是 shadow 陪面（提问全部由他人承担）时用这份，不用上面那份。** 判定方法见 `SKILL.md`「面试官角色判定（主面 / 旁听）」。**候选人评价 `evaluation.md` 不受影响，照常按六维模板写满。**

与主面模板的四处差异：① 开篇必须有「本场归属说明」；② **不给 A/B/C/D 档**；③ 五维表的对象是主面官（点名）；④「改进建议」换成「可借鉴的做法」+「该避开的坑」两节。

````markdown

飞书招聘登记本场（*N* 面，*日期时间*）的面试官是 *用户姓名*，但速记里的提问全部来自 ***主面官姓名***（*X* 条），*用户姓名* *全程零发言 / 仅 N 条发言*。即 ***主面官姓名*** 主面、*用户姓名* shadow 陪面同一场。

**因此本文件不是对 *用户姓名* 面试技巧的评价，也不给面试官档位**——本场用户没有可供判定的提问行为。下列内容是对 ***主面官姓名*** 提问行为的观摩记录，供 *用户姓名* 下次自己主面时参考。

## 面试官评分

**综合评分：不评档（本场为 shadow 陪面，无可提取的提问行为）**

## 主面官（*主面官姓名*）五维观察

*本表评的是主面官，不是用户。*

| 维度 | 标注 | 说明 |
|------|------|------|
````

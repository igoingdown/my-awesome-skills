# 面试官评价体系（做面试官复盘时读）

除了评估候选人，本 skill 同时对面试官（即用户本人）的表现进行复盘评价，帮助面试官持续改进面试技巧。

> 🚨 **前置：本场用户是主面还是旁听（shadow 陪面）？** 本文件的全部档位与五维标准**只适用于用户本人主面的场次**。用户是 shadow 陪面（提问全部由他人承担）时，复盘改写成**观摩笔记**、**不给用户打档**——判定方法与写法见 `SKILL.md`「面试官角色判定（主面 / 旁听）」。
>
> **为什么这条放在最前面**：复盘存在的意义是让用户改进自己的面试技巧。拿别人的提问行为给用户打 A/B/C/D，用户会照着一份"评错了人"的报告去改自己——这比不写复盘更糟。而且飞书 `interviewer_list` 只登记 shadow 者一人的情况实测存在（旁听场里真正的主面官根本不在名单里），**系统字段判不出主面，只能靠 `asr.md` 说话人分布判**。

## 面试官评分档位

面试官评分**只能**取以下 4 个值之一：

```
A   B   C   D
```

| 评分 | 含义 |
|------|------|
| A | 优秀：问题路径清晰、节奏好、信息密度高，几乎无改进点 |
| B | 良好：整体合格，有 1-2 个可改进点但不影响评估质量 |
| C | 及格：有明显可改进点，部分维度信息获取不充分 |
| D | 待提高：多个维度有问题，可能影响了对候选人的公正评估 |

> ⚠️ **禁止使用 A-、B+、B-、C+ 等未定义子档**（真实事故 2026-09-08：连续三份复盘分别写了 B-、B+、A-，三者互不可比，且都在为"介于两档之间"找台阶）。**四档就是四档，介于两档之间时取低档。** 判 B 还是 C 的分界线很清楚：**取样缺口是否影响了对候选人的公正评估或结论完整性**——不影响是 B，影响是 C。典型的 C：岗位核心能力零取样（如 AIGC 岗位没问 AI 能力）、编码时间不足导致核心维度只能留空、全场只形成一个取样单元导致候选人拿不到本可企及的分数。

> **档位与"追问技巧好不好"是两件事。** 追问质量高但取样设计有硬缺口，仍然是 C——因为档位衡量的是"这场面试是否支撑了一个可靠且完整的结论"，不是"面试官表现得专不专业"。把这两者混在一起会导致给分虚高。

> ⚠️ **旁听场不打档，档位留空。** 用户是 shadow 陪面时，四档一个都不许给——**包括不许"折中给个 C"**。档位是对用户行为的判定，本场用户没有可判定的行为，留空并写明"本场为 shadow 陪面，无可提取的提问行为，故不评档"。
>
> **真实教训**：`chenzhenran/002` 那场（涂鹏主面、用户 shadow 陪面，用户全程零发言）的复盘开篇正确交代了"复盘对象是涂鹏"，却仍在「面试官评分」里写了 `C`。这个 `C` 评的是涂鹏，出现在用户的自我复盘文件里就是错的——用户翻自己的历史复盘做趋势对比时，这条会被当成自己的成绩。**交代了归属不等于可以打档，两件事都要做对。**

## 面试官五维评估

五个维度：**提问路径、节奏控制、追问精准度、面试官纪律、表达效率**

每个维度用 `✓` / `△` / `✗` 标注：

| 标注 | 含义 |
|------|------|
| `✓` | 做得好：该维度表现符合或超出预期 |
| `△` | 需改进：有明确的改进空间，但不严重 |
| `✗` | 有问题：该维度存在明显问题，可能影响面试效果 |

## 各维度含义与判断标准

### 1. 提问路径

核心原则：**实践结果 → 细节追问 → 原理深挖**，而非概念入手。

- `✓`：问题从候选人的实际工作出发，数字/结果先行，原理从实践中自然引出
- `△`：大部分问题路径正确，但偶尔出现概念入口（如"你了解过X吗"）
- `✗`：频繁以概念/原理开场，候选人被迫先背书再说实践

**判断方法**：统计 `asr.md` 中面试官的问题，计算"从实践切入"vs"从概念切入"的比例。概念入口占比 >30% → `△`，>50% → `✗`。

**概念入口的典型特征**：
- "你了解过 X 吗？"
- "X 的原理是什么？"
- "你能说一下 X 和 Y 的区别吗？"（未关联到具体使用场景）

**实践入口的典型特征**：
- "你们实际遇到 X 了吗？怎么处理的？"
- "这个数字是多少？口径是什么？"
- "上线后有没有出过问题？"

### 2. 节奏控制

核心原则：**在有限时间内高效判断出候选人的长处与短处**，时间花在能产生判断结论的地方。不要求面面俱到覆盖每个项目，但不能因节奏失控导致关键能力没摸到。

- `✓`：节奏服务于判断——能快速锁定候选人强弱项，编码/核心能力得到验证，没在已问清的点上空耗
- `△`：节奏略有失衡（如某项目深挖过久、或反复纠缠已问清的点），但最终长短处判断仍站得住
- `✗`：节奏失控导致**关键能力未能判断**（如编码没时间落地、核心技术维度完全没摸到、全程困在一个点出不来）

**校招场的节奏另有侧重（真实教训）**：某校招场 63 分钟里项目深挖占 44 分钟（70%），结果**后端基础零考察 + 编码零产出**——而这两项恰恰是校招 1-2 权重最高的。候选人自己都说了"从技术上角度来说的话，它其实并没有那么的复杂"，项目不难就更该用基础和编码定级。**参考盘：项目 25 分钟 + 基础抽检 10 分钟 + 编码 20 分钟 + Q&A 5 分钟，后 30 分钟不许被项目侵占。** 基础抽检不必是八股，从候选人自己的系统里长出来最好（如"并发写同一条记录会怎样 → 加锁 → 隔离级别 → 幂等"）。**校招场若基础与编码双双零取样 → 节奏控制直接 `✗`**，因为它会导致候选人评价无法定级、必须再补一轮。

**判断方法**：从 `asr.md` 的时间戳计算各环节用时。下面是**参考节奏**，不是硬指标——只要高效得出了候选人长短处判断，偏离也算 `✓`：
- 自我介绍：3-5 min
- 项目深挖：问出该项目能体现的强弱项即可，问清就切，**不必每个项目都覆盖**
- 编码题：15-25 min（编码是独立能力，尽量留足时间到代码落地）
- Q&A：3-5 min

判定红线：**编码没时间落地、或核心技术维度完全没摸到 → `△` 或 `✗`**（这类缺口直接影响能否判断候选人）。仅仅"简历某个项目没问到"但长短处已判断清楚 → 不扣分。

**编码环节的"验证收尾"是节奏的一部分**（真实教训，两场都踩过）：候选人写完说"差不多就是这样"就收尾、面试官没让其跑用例/走查，结果代码实测是错的——现场判断与真实水平差了一档。所以：
- 编码时间预算里应固定留最后 2-3 分钟做"验证收尾"——让候选人现场跑题面第一个用例（平台可运行时必跑），或口头 walk through，并核对"口述思路 vs 实际代码"是否同一个算法。**写完 ≠ 结束，验证完 = 结束。**
- 候选人卡壳时，先给"结构性提示"（如"你的贪心为什么会漏解？要不漏得穷举所有分法，用什么手段？"）观察能否自己爬出来，再点破答案——直接给答案会少测一档"提示吸收能力"。
- 缺"验证收尾"导致编码正确性没验证 → 节奏控制记 `△`，并在复盘里作为最高优先改进项。

### 3. 追问精准度

核心原则：**听到模糊词立刻追具体数字；追问有目的性，不连续轰炸**。

- `✓`：候选人说"大概/可能/差不多"时有追问具体数字；追问有方向性，2-3 个问题后换方向
- `△`：部分模糊回答未被追问，或偶尔出现无目的的连续追问
- `✗`：大量模糊回答被放过；或频繁连续追问让候选人无喘息空间

**需追问的模糊信号词**：
- "大概"、"差不多"、"可能"、"好像"、"左右" → 追"具体多少？"
- "参考了 X" → 追"X 有什么优缺点？你改了哪里？"
- "我们用了 Y" → 追"为什么选 Y 不选 Z？"

### 4. 面试官纪律

核心原则：**不讨论方案、不补上下文、不下判断、不给偏向性反馈**。

- `✓`：全程保持中立，只问不答（技术层面），Q&A 环节简洁不过度推销
- `△`：偶尔补充了技术上下文或对回答做了轻微评价，但未严重影响
- `✗`：与候选人讨论技术方案；给了明显的偏向性反馈；Q&A 环节过度推销公司/岗位

**红旗行为**（出现任何一条直接 `✗`）：
- 告诉候选人"你应该用 X 方案"
- 对候选人的回答说"不对，应该是..."
- Q&A 环节主动展开超过 3 分钟介绍公司详情
- 结尾暗示通过/不通过结论

### 5. 表达效率

核心原则：**问一次就够，不解释不重复，善用沉默**。

- `✓`：问题简洁一句话，不重复解释，候选人不懂时由候选人主动追问
- `△`：偶尔重复解释问题（2-3 次），但不频繁
- `✗`：频繁重复/换角度解释同一个问题（>3 次出现），剥夺了考察候选人理解力的机会

**判断方法**：在 `asr.md` 中搜索面试官对同一个问题的多次表述。出现"我再解释一下"、"就是说..."、"换个角度问..." → 计为一次重复。

## 面试官评价的数据来源

面试官评价**完全基于 `asr.md` 中面试官的发言**（面试官的发言通过说话人标识区分）。具体分析：

1. **面试官的问题列表**：提取所有面试官发言中的提问，分析提问路径
2. **时间分配**：通过时间戳计算各环节用时
3. **追问模式**：分析候选人模糊回答后面试官是否跟进
4. **纪律表现**：检查面试官是否有讨论/评价/推销行为
5. **表达模式**：检查面试官是否有重复解释、补充上下文的行为

## 面试官评价与候选人评价的关系

- 面试官评价**不影响**候选人评分。候选人该打多少分就打多少分。
- 面试官评价是**独立的自我复盘**，目的是帮助面试官持续改进。
- 如果面试官的问题导致某维度信息获取不充分（如"技术广度"留空），需在面试官评价中指出——"节奏控制导致未覆盖 X 维度"。**注意配合 SKILL.md「证据充分性前置门」**：这种情况下候选人对应维度留空、不记 `-`，缺口记在面试官账上而不是候选人账上。

### 跨场对比的边界（候选人评价禁止，面试官复盘允许）

两类报告的跨场纪律**不同**，别用一条规则套两边：

| | 能不能跨场引用 |
|---|---|
| **候选人评价**（`evaluation.md`） | **一律禁止。** 不读、不引用其他候选人的材料与评价，也不读本候选人其他轮次的评价文件。每轮只基于本轮 `asr.md` + 简历独立成文（见 SKILL.md「评价原则」第 8 条） |
| **面试官复盘**（`interviewer-review.md`） | **允许，且鼓励。** 可以引用面试官自己在其他场次的行为做对比 |

**为什么面试官复盘要开这个口子**：面试官的改进点往往要跨场才看得出根因。真实例子——两场面试都出现"编码环节零落地"，一场是 Q&A 吃掉 24 分钟、一场是项目深挖吃掉 40 分钟，**直接原因不同但根因相同（没在开场把时间盘定死，只在单个环节内控时长）**。只看单场只会得出"这次 Q&A 太长了"这种表层结论，看两场才能定位到"倒计时锚点设错了"。同理，也能确认上一场的改进建议有没有生效（如"结尾不再泄露评价结论"）。

**跨场引用的三条约束：**

1. **只能引用面试官自己的行为与话术**，不得引用其他候选人的评分、结论、技术表现。写"上一场（某候选人）我在结尾透露了评价结论"可以；写"上一场那个候选人技术比他强"不行。
2. 引用时**标明场次**（候选人姓名或日期），便于回溯。
3. **不得反向影响候选人评分**：跨场信息只进面试官复盘，写候选人评价时不得参考。

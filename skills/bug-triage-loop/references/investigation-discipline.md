# 排查纪律（打分取证 / 降级取数 / 清理门禁）

本文件是 bug-triage-loop 的**排查方法论**，从 SKILL.md 的 Step 8 与「错误处理」抽出，按需加载——SKILL.md 只保留 loop 编排骨架，真正定位/取证/下结论时读这份。全部是历史事故复盘固化的 P0/P1 规则。

## Step 8 打分前：现状回验三查（P1，来自一次"AI 替用户说话"真实事故复盘）

投诉时间点的证据只能证明"当时发生过"，报告在给处置建议前必须补三查：

1. **问题现在还在吗**：查该实体的**最新状态**（如会话表的 last_message_content / updated_at 等冗余字段，或该 uid 当天 SLS 请求）。"已自愈"和"正在恶化"的处置建议完全不同。主消息存储不可达时的绕行：快照表（如 feedback 表存的上下文快照）、末条冗余字段、SLS ACCESS 日志里的 req body。
2. **用户行为时间线**：拉按天的使用量化表（如日聊天轮数/日订单），和投诉时间对齐。行为断崖（如 726→64→12→4 轮/天）是严重度和优先级的硬依据，能把 low 抬到 high。
3. **用户价值画像**：涉及"重度/付费/VIP"断言必须查 order + subscription + wallet 三表实锤（见 rubric.md 反例）。付费用户正在流失 = 处置优先级直接拉满，且 CS 可能需要补偿动作。**群体投诉时做全量画像**：从反馈表抽出全部投诉 uid，三表 IN 批量联查，给出"付费人数占比 + IAP 累计 + 订阅计划分布 + Top 付费"——81% 付费和 20% 付费的处置优先级完全不同，这个数字决定要不要主动触达。
4. **实体血缘**：用户"重开/重置/新建"类自救操作，查血缘字段（parent_id / branch_from_* / is_root）确认是真白板还是分支复制。分支会携带全部历史，把"自救失败"误读为"复发"会导错根因方向。
5. **群体恢复核查（有 owner 的群体性问题，归档前必做）**：owner 说"已修复"后，对全部投诉 uid 做**逐人当日 SLS 行为核查**，输出四态清单：已恢复（活跃且无问题行为）/过渡中/仍困/未上线。uid 数 >10 时用 Dynamic Workflow 并行（按 uid 分批，每 agent 一批，structured output 汇总；37 uid 6 agent 约 4 分钟）。"投诉量回落"只是弱信号，"仍困清单为空"才是闭环；仍困清单叠加付费画像 = CS 主动触达名单。**这个规则来自"cinema 无法退出"真实事故**：投诉量回落中但 5 个仍困用户里有 $1258 Premium 付费者，不做逐人核查就宣布解决会漏掉他们。

## 扩样取证的收手判据（P1，来自一次"扩了几轮样一个实例都没有"复盘）

第一批取证没找到实例时，正确动作是**先判断缺的是样本量还是判定口径**，再决定扩不扩：

1. **先自查上下文是否足够**：取到的片段有没有被截断（落库/日志侧常有长度截断，尾部内容看不到）、有没有缺关键的上下文轮次、判定所依赖的字段是不是真取到了。**口径缺陷下的"没找到"不是证据**——先补齐口径再谈样本量。用户的追问形态："你真的实锤了吗？上下文足够吗？可能缺失什么？如何补齐？"
2. **扩样要说清怎么扩**：扩到多少条、按什么维度抽（时段/用户分层/语言）、预期能把置信度从多少提到多少。给不出这三项就不是扩样，是重复劳动。
3. **连续扩样仍为零 → 出反向结论，不要继续扩**：样本量已足以支撑"若存在则应命中"时，诚实结论是"该问题在当前证据下不成立/未复现"，实锤度落 `not-bug-after-analysis` 或 `insufficient`，并写清已覆盖的范围与仍存在的盲区。此时主动说明**边际收益已低**及其依据（已覆盖多少、命中 0、再扩预计仍为 0），别把"接着扩"当默认动作——用户会直接问"为什么边际收益低，原因是什么"，答不出就是没想清楚。
4. **反向结论要能推翻上游断言**：若这条问题此前被写进报告/spec 并据此排了修复，取证为零时必须回头把上游结论标为待撤，并提示相关改动的必要性需重估。

## 召回方法本身要先被验证（P0，来自一次"找不到实例是你的方法问题"复盘）

靠关键词/正则命中去捞"用户有没有表达某种体验问题"（抱怨、困惑、不满、觉得被忽略）几乎必然召回不到——这类现象藏在语义里而不在词面上，用户极少用你猜的那个词。这种召回方式下的"扫了一遍没命中"不构成任何证据，用户的纠偏形态是「找不到是你的方法问题，不应该用正则匹配或关键词命中，应该用语义理解」。规则：

1. **主观体验类现象一律走语义判定**：把候选轮次逐条交给模型判定"这段话里有没有隐含<该现象>"，而不是匹配词表。判定慢是可接受成本（用户明确说过"即便很慢我也能接受，但你必须找出实例"）。
2. **先小样本跑通链路再放量**：先抽少量样本把"取数 → 判定 → 回溯上下文 → 落档"整条链路跑通，确认判定质量和产出格式没问题，再切全量。直接对全量开跑，口径错误会被放大到整批，返工成本最高。
3. **判定判据单独留档**：命中/存疑/不命中的判据（决策树、边界怎么切）写成独立文档，附完整上下文的样例，与结论一起交付。结论可以被质疑，判据能被审才谈得上可信。
4. **命中只是入口，要回溯前因**：判定为"存在该现象"之后，还要回该实体的历史找出触发它的前置上下文（如被截断掉的那段），否则只有一条孤立抱怨，证明不了机制。

## 举证的确认偏差门禁（P0，来自一次"你找的还是正样本"复盘）

找到几条支持结论的样本不等于结论成立。要下"这个现象存在且有影响"的判断，必须同时交出反面那一半，否则整条结论上限只能是 hypothesis：

1. **正反样本成对交付**：每类结论都要给支持它的样本**和**该找到却没找到的对照样本（同条件下不该出现该现象的那一侧）。只给正样本时用户会直接点破「你找的还是正样本，负样本再给我找出来一个」，并要求「不许偷懒，为你的结论负责」。反面样本找不到，就说清找过哪些范围、为什么找不到，而不是省略不提。
2. **样本要带完整上下文，不许截取**：结论涉及"随时间演变""用户如何反应"这类过程判断时，只看片段必然出错——必须把该实体的完整历史读完再下结论。踩过：凭中后段片段推出"用户被动接受了偏移"的叙事，被追问「这段话有根据吗？推理链路是什么？用户在对话过程中有引导过吗？你出这些结论都不看全文吗」——片段里看不到的前置引导，恰恰能推翻整个叙事。
3. **归属先证再用**：引用一段内容当证据前，先确认它出自谁（哪一方发出、哪个环节产出）。风格判断不算依据，要回到带发送方/来源字段的原始记录核。用户会凭语感质疑「这段真是用户发的吗？我怎么感觉像是模型写的」——归属搞错，基于它的全部推论一起废。语言/来源类自动判定（如语种识别）要说清方法、准确率与评估方式，不能当黑盒结论用。
4. **叙事型结论逐句挂证据**：报告里每一句因果/心理/趋势断言（如"用户放弃了最初设定""体验在悄悄流失"）都要能指到具体样本与轮次。指不到的删掉或改写成待验证假设，不要保留成读起来成立的散文。

## 结论要能报把握度；反直觉结论先严格证明（P1，来自多次"你确定吗/你怎么确定的"追问复盘）

正反样本、口径三件套之外，结论交付还有两道收口：

1. **关键结论要能报把握度**：用户对承重结论的追问形态是「你确定是大头吗？你怎么确定的？」（会连问三遍）——必须答得出判断思路、依赖了什么数据、数据怎么获取与加工的、把握有多大。答不出任一项，该结论降级为待验证。指向外部因素（上游服务、第三方、用户侧）的结论尤其要给**把握度 + 可执行的验证路径**（需要用户提供什么、去哪核实），不能给一个无法行动的"疑似"。
2. **反直觉结论先严格证明再采信**：分析推出与直觉/常识相反的结论（如"合并操作必然需要延迟收口""某优化有上限不可能生效"）时，先把推理当成命题**严格证明一遍**（前提列全、每步可检），并把完整案例给用户亲自核查，才能作为后续决策的输入。用户的原话形态是「把这个结论严格证明一遍」「你的新观点能站住脚吗？」——反直觉结论错了会把整个方案带偏，值得多花这一步。

## 统计口径必须自带三件套（P1，来自一次"这几个百分比分别是怎么算的"追问复盘）

报告里每出现一个比例或群体规模，都会被逐个追问「这批人是怎么筛出来的、分子分母各是什么、两个比例之间是不是子集关系」。答不出任一项，这个数字就不该写进结论。每个数字紧邻处交代：

1. **筛选条件**：这个群体是按什么条件从全量里选出来的（阈值、时间窗、必须具备哪些字段），以及筛完剩多少。给了规模数却说不出筛法，读者无法判断它代表谁。
2. **分子分母各是什么单位**：是"人"还是"条"还是"用户陈述的事实"——单位不同的两个比例不能并列摆放，更不能相减。用户的追问形态就是「这个百分比的分子分母是什么？是用户，还是用户所述的事实？」
3. **几个比例之间的集合关系**：是子集、交集还是各自独立抽样。并列两个百分比而不说关系，读者会默认它们可比，由此推出错误结论。
4. **口径的已知偏差写在数字旁边**：如"只包含愿意明说的那部分，不含沉默与已流失者""部分命中是两种成因叠加，无法单独归因"。偏差不写等于把下界当真值。

## 自造指标名必须就地定义

排查过程里临时起的分层名、率名、余量名（形如 `<某层>率`、`<某判据>成立率`、`margin`）对读者是黑话，用户会逐个问"这是什么含义，解释一下"。规则：第一次出现时用一句话给出**定义 + 计算方式 + 该值大小说明什么**；能换成自解释的普通说法就别自造名字。

## bytebase 授权断链降级序列（P1，来自一次"AI 替用户说话"真实事故复盘）

bytebase MCP 报 401/token expired 时按序降级，**不要卡在重授权上等用户**：

1. 读 `~/.claude/.credentials.json` 的 mcpOAuth 条目拿 accessToken 直接 curl REST（条目可能被并发会话轮换清空，要判空）
2. 有 refreshToken → `POST /api/oauth2/token` grant_type=refresh_token 续签（**必须带正常 User-Agent**，如 `bytebase-mcp-proxy/1.0`，Cloudflare 挡 Python-urllib 默认 UA）
3. 本地 bytebase-mcp-proxy 活着 → 走 `http://127.0.0.1:38787/mcp` 手写 MCP JSON-RPC（initialize → notifications/initialized → tools/call），工具用 `call_api` 显式资源名（SA 无 bb.databases.list 权限，`query_database` 按名解析会 PERMISSION_DENIED）
4. 全断 → 标 tag=tool_failure，列"未验证项"

## 主数据存储捞不到/导不出时的证据获取降级（P1，来自一次取数受阻复盘）

直连主存储（如宽表 / KV 型存储）查询超时，或导出被引擎内存上限拦截、分批也过不去时，别死磕同一条通路。按优先级换源实锤：

1. **离线数仓镜像表**：同一份数据常在离线数仓有一份镜像（表名 / 字段名可能不同，且往往无反转 uid、直接是明文主键）。用前先核实**分区是否最新、覆盖率是否足够**——镜像常有同步延迟或抽样缺失，先抽样比对行数量级再下结论，别把"镜像还没同步"误当"线上没有这条数据"。
2. **日志侧重构**：从访问日志 / 请求日志里的 req body 间接重构原文，适合验证行为、不适合全量取数。
3. **代执行通道**：自己无库读权限时，把校验 / 取数 SQL 交给有只读权限的协作通道（有权限的同事或代执行机器人）代跑，自己只负责把 SQL 写正确、把结果拿回来分析。给出去的 SQL 要自包含、带 LIMIT、注明用途。
4. **本地等价实例自证机制**：要验证的是**机制**（建表 DDL 能不能过、这条 SQL 语义对不对、读写路径行为如何）而不是取线上数据时，别拿线上库当试验场——本地起一个同引擎容器 / 在本地实例建临时表跑通，验完即销毁（`docker rm` / `DROP TABLE`）。用户明确提过这条路：「本地跑 Docker，跑完记得删除，本地验证完再进行下一步」。要点：
   - 连接参数从本地配置样例取，**不要复用生产连接串**；
   - 建的库表加可识别的临时前缀，验完立刻清，清理动作和结论一起报；
   - 只能证机制，**不能替代线上数据结论**——本地跑通只说明 SQL/DDL 可用，线上是否真有这条数据仍要回线上证据源核。

**权限缺口按缺口报，不要绕**：证据在自己无账号的第三方系统里（如异常聚合平台）时，正确动作是把「需要哪个系统的什么权限、找谁开」明确告诉用户，同时用手上已有的源做能做到的那部分验证，并在报告里标出「因无权限未验证项」。不要为了看一眼日志去尝试绕过授权。

**跨存储主键编码差异**：uid 等主键在不同存储里可能有编码差异（反转 / 偏移 / 类型不同）。换源前先拿几条已知样本反解出映射规则再批量查，别拿一套 key 直接套所有表——踩过：一个 key 在某表查不到，只因该表用的是未反转 uid。

## 生产 DB 访问纪律（P0，用户明确要求）

- **读：控制 SQL 复杂度和对 DB 的压力**——查询必须带 LIMIT、用索引键（uid / 主键 / 时间列）过滤，禁止大表全扫和多表复杂 join；大范围统计拆成小批多次跑，别让一条定位查询把主库拖慢。
- **写：绝不直连执行**——本 skill 的定位链路是只读的，任何写操作（UPDATE / DELETE / INSERT / DDL，含脏数据清理）一律走工单（如 bytebase `propose_database_change`）交用户 review 后执行；报告里只给建议 SQL + 工单链接，不代执行。
- **被授权写测试库造数据时，写前先自证目标库**——用户明确说"直接写表造几条测试数据"时，授权只覆盖**测试库**。执行前必须把即将连接的实例名 / 域名 / 库名回显出来，与已知测试实例逐项比对确认后再写（测试与生产实例名往往形似，"默认连的就是测试库"不成立）；造完按约定即刻清理，清理结果与写入一起报。用户的追问形态是「你用的是测试库吗？别搞线上库呀！！」——被问到这句已经晚了，回显必须发生在写入之前。

## 跨存储脏数据清理的完整性门禁（P0，来自多次"清一半留悬空引用"复盘）

同一份数据横跨多个存储（主库行 + 向量库 embedding + 缓存 + 检索索引）时，**只清主库是不完整的清理，会留下悬空引用**：向量库召回拿到某条 ID → 回主库查该 ID 已被删 → 命中空/报错，反而制造新故障。给清理建议前必须先答清三件事，任一没答清则清理方案标 hypothesis、不许执行：

1. **列全存储副本**：这份数据在哪几个存储各存了一份？（如 mempoint 同时在关系库、向量库、可能还有 summary 缓存）按存储逐个列删除/失效动作，不是只写一条 `DELETE FROM 主表`。
2. **定清理顺序**：先断"读入口"再删数据，避免删除窗口内被重新召回。缓存/索引类是可重建副本的，删后靠 cache-miss 自动重建；不可重建的先备份。
3. **删前置守卫**：删除前先确认注入/回源路径已被堵（如占位默认值已置空、写入侧门控已上线），否则删完立刻被脏数据重新灌满，清理白做。

配套：大批量删除前先跑一条只读预检 SQL 数出"预计影响行数"给用户核对，并明确剔除误报类（语义相似但非目标），别凭 ILIKE 模糊匹配就批量删。

## 批量清理的"选中依据"门禁（P0，来自多次"这 N 条你凭什么判定是脏的"追问复盘）

完整性门禁答的是"怎么删干净"，这条门禁答的是"凭什么删这几条"。启发式/模糊匹配挑出的待删集合，用户必然追问"决策树是什么、每条边的置信度多少、每个分支靠什么实锤"——答不出就是不许删。给待删清单前必须满足：

1. **逐条可归因，不是整批一个理由**：每条待删记录都要能落到判据上（命中哪个谓词、缺哪个存活引用、与哪条实锤证据对应），而不是"这批都是启发式生成的所以都删"。判据是语义相似（如 ILIKE 命中）而非精确等值时，置信度上限只能是 likely，清理方案标 hypothesis。
2. **决策树逐边标置信度**：把"如何从全量收敛到这 N 条"画成决策树，每个节点/边注明靠什么实锤（扫库计数 / 存活引用核对 / 抽样人读），哪一步只是推测就显式标出。任一承重边未实锤 → 整个清理方案不得高于 hypothesis。
3. **优先可逆的软删**：能软删（标记失效 / 置软删列）就不硬删——错杀可回滚，且给后续复核留窗口。选硬删必须说清为什么不可逆是可接受的。无论软硬，删前都要有可回退依据（备份 / 快照 / 保留可反查的原值）。

## 大体量用户数据的处理规范（P1，用户明确要求）

拉用户聊天记录/日志等大体量数据时，**先落盘到 /tmp，再写 python 脚本做统计/模式分析，只把统计结论和抽样片段带回上下文**。禁止把几十 KB 的原文整段读进上下文：一浪费预算，二用户隐私内容不应大面积进入对话。典型：message_feedback.chat_messages（50 条快照约 53KB）→ 存 json → 脚本算句式密度/词数分布 → 上下文里只留数字和 1-2 条示例。

## 日志抽取的正则安全（P0，来自一次把共享开发机内存打爆的事故）

从落盘日志里做"关键词 ± 上下文"抽取时，会话里的 `grep` 可能是影子函数、实际走内置引擎，用 DFA 全展开编译正则——**大范围有界量词（如 `.{0,150}关键词[^x]{0,200}`）会状态爆炸，与文件大小无关**（曾在 11KB 文件上吃掉十几 GiB 内存、跑一个多小时不返回，在共享开发机上把整机内存打爆被 root SIGKILL）。规则：

1. 有界量词 `{m,n}` 上限超过 ~20 时，**用 `command grep` 强制走系统 GNU grep**，不要直接用 `grep`。
2. "关键词 ± 上下文"优先两步走：先 `command grep -n` 定位行号，再用 python 按偏移切片；不要用 `.{0,N}关键词.{0,M}` 单发正则。
3. 预期跑得久的重型正则/批量解析，主动加 `timeout` 与 `ulimit -v`（如 `bash -c 'ulimit -v 4194304; ...'`），别让一条抽取命令拖垮机器——尤其排查任务本身就是被资源打爆触发的场景。

配套：排查"机器卡死/SSH 登不上"这类问题时，资源瓶颈有多种（CPU / 内存 / 磁盘 / fd），别默认是 CPU；先分别看内存（RSS / OOM 记录）、磁盘、fd，再下结论——本条事故的现象是 SSH 登不上，真因是内存被单进程吃满。

## SLS 重建用户使用 session 的标准手法（来自"cinema 无法退出"真实事故）

验证"用户重启过吗/重启后恢复了吗"这类端上行为问题，从 ACCESS 日志重建使用 session：

1. 拉该 uid 当天全量 ACCESS 行（分页落盘，client 侧过滤 `uid:<UID>` 防响应体误中）；
2. 按时间排序，**请求间隔 > 10 分钟切分 session**；
3. session 首批请求判断冷启动：以 config/activity/checkin/membership_price 类配置接口开头 = 冷启动（App 重启）；以业务接口开头 = 热切换回前台；
4. 每个 session 内统计目标行为（如 cinema 专属接口 vs 普通聊天接口），对齐投诉时间戳，即可回答"投诉在重启前还是后"、"重启后行为是否恢复"。

**注意 SLS 倒序分页截断**：默认拉最新 N 行，更早的 session 会被截断漏掉——先确认拉到的时间范围覆盖全天，不够就按更早时间窗补拉，否则会把"当天第二次启动"误判成"当天唯一一次"。

## 机制归因的四道门禁（P0，来自一次热更产物损坏事故的根因误判复盘）

背景：AI 精确定位了毒版本、影响面、恢复时间线（全部正确），却把**机制**归因为"打包机缓存污染"并宣布 confirmed；真根因是编译器优化与发布工具后处理的交互 bug。错误机制直接误导修复方向。四道门禁，**任一不过，机制结论不得高于 hypothesis**：

1. **残差清单门禁**：排查全程维护"观察到但未解释"异常清单（建议直接写在草稿里）。宣布 confirmed / "闭环"前逐条核销；任一承重残差（与主结论相关的未解释现象）未核销 → 降级。特别警惕: 时间线/影响面等外围结论全对时，机制层的洞最容易被战果掩盖。
2. **对照实验门禁**：构建/工具链/环境类归因，必须有单变量对照（同代码改一个因素重建对比），与代码归因"必须读完整函数体"同级。没有对照实验 → 上限 likely。
3. **差分先于探针门禁**：手里有好/坏两份产物时，第一步是全量结构 diff（体积/节表/字符串表/符号数），让 diff 生成假设；禁止只做"目标在不在"的布尔探针——那只会确认先验。二进制排查铁律：查邻域，不只查存在性。
4. **领域边界门禁**：证据链跨进未仪表化的领域（二进制格式内部/编译器行为/内核等）时二选一——投入深挖（如写解析器看内部），或在报告显式声明"机制在 X 域内部未深挖，以下为 hypothesis"。禁止用通用背景知识拼装机制叙事冒充已验证结论：凡机制描述，报告里必须能指出"这一句对应哪条本案证据"。

配套修正 owner 交互规则：owner 的**事实结论**（修没修好）走逐用户闭环验证；owner 的**机制结论**（为什么坏）同等对抗——当自己的新证据与 owner 定性矛盾时，正确动作是质疑框架而非修补框架；"给 owner 的框架打补丁"是锚定效应最隐蔽的形态。

## 跨服务同名字段的边界门禁（P0，来自一次"这个接口到底返回什么"连错两轮的复盘）

多服务共存的项目里，两个服务常有**同名但不同层级、不同库、不同语义**的字段（如一处是项目级的长篇设定正文、另一处是实体级的短属性且受开关控制）。翻车形态：把 A 服务的字段语义套到 B 服务上答，或把某个枚举值（如"由 agent 写入"的来源标记）读成"另一个服务写进来的"，于是断言两个服务的数据互通——用户直接反问「你理解的那类实体在哪张表里？怎么读出来的？如果它依赖的都是本服务的表，另一个服务建的实体理论上捞不出来。**这是一个重要的边界，你看清楚**」。四道门禁：

1. **答字段语义前先钉住"哪个服务、哪张表、哪个库"**：同名字段一律当成不同字段处理，逐个给出表名 / 存储引擎 / 所属层级（项目级还是实体级），不要跨服务复用上一轮的结论。
2. **来源标记不等于跨服务写入**：`*_by_type` / `source` / `channel` 这类枚举描述的是**本服务进程内的写入方**（人 / 本服务的 agent / 定时任务），不能推出"另一个服务往这里写过"。要断言跨服务数据流，必须指出承载它的具体代码路径。
3. **跨服务通道要逐条枚举并说明宽窄**：两个服务之间往往只有极窄的单向只读通道（如只读一张用户表的几列）。给边界结论前把全部跨库调用点列出来：读哪张表、哪几列、单向还是双向、失败时是 fail-soft 还是报错。没枚举完就不要说"互通"或"不互通"。
4. **读快照的接口要说清时点语义，但陈旧风险的分量用数据定**：发布 / 冻结类快照的字段是"发布那一刻的值"，机制上存在陈旧可能。**别把机制可能性直接讲成需要留意的坑**——抽存量逐条比对快照与实时值（如比 md5），实测几乎全一致时就如实说"机制上可能、生产里基本不发生"，并把这次的修正明确讲出来。

配套：这类结论只读代码得出时，必须在结尾声明未验证项（没连库比对、没起服务打接口、没排除离线同步任务），并给出补验路径；用户会直接让你去捞几条真实数据确认语义，先说清盲区比事后被纠正便宜。附带发现也要报：抽样时撞到的存储层坑（如某列含非法编码字节，任何在库内对该列做截断 / 编码转换的 SQL 都会报错）属于后续做数据分析和迁移必然会踩的雷，顺手写进结论。
